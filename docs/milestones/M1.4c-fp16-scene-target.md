# M1.4c Evidence: FP16 Scene Target Migration

- Status: Accepted implementation slice
- Date: 2026-07-19
- Parent slice: M1.4 scene-linear HDR and transparent composition
- Reference extent: 3840x2160

## Result

Both graph and selectable legacy modes now allocate `litScene` and its transparency
copy as `VK_FORMAT_R16G16B16A16_SFLOAT`. Lighting and forward render-pass contracts
use the same format. This slice deliberately retains the legacy fitted curve inside
lighting, isolating target precision and reuse from the upcoming scene-linear shader
interpretation change.

The compatible FP16 copy can reuse one expired FP16 GBuffer slot. The maximum graph
still has nine passes, eight logical resources, and 25 transition intents, but now
uses six rather than seven engine-owned physical slots. The executor test asserts
that `scene.opaque-copy` actually shares an expired `gbuffer.*` slot.

Legacy final capture remains a BGRA8/sRGB TGA contract. FP16 readback is converted
after fence completion with the tested IEEE half decoder and the CPU sRGB reference
transfer. This conversion occurs only for a requested, already timing-excluded
capture frame. M1.4's later scene-linear capture will instead retain float values in
the accepted PFM contract.

## Verification

- Debug and Release builds succeed; both full suites pass 12/12 tests.
- Graph-mode Debug Vulkan validation is clean for 4K nested transparency and opaque
  emissive; the legacy fallback is also clean at 4K.
- Nested-transparency comparison to M0: maximum RGBA delta 2, p99 maximum RGB delta
  1, changed-pixel fraction 0.107251, mean luma SSIM 0.99996175.
- Opaque-emissive comparison to M0: maximum RGBA delta 1, changed-pixel fraction
  0.00861449, mean luma SSIM 0.999994.

The localized image change is expected: the old path quantized lighting into an
8-bit sRGB intermediate and decoded it again before presentation; the FP16 path
retains the tone-mapped linear value until the final swapchain encode. It removes an
intermediate quantization rather than changing the curve. Evidence is under
`out/captures/m1.4c-*`, `out/comparisons/m1.4c-*.json`, and
`out/profiles/m1.4c-debug-*.jsonl`.

## CPU, GPU, and memory

Three Release 4K `transparency_v1` runs (200 warmup, 3,000 measured) produced CPU
medians 0.5634/0.5371/0.5381 ms and GPU medians 0.4456/0.4424/0.4420 ms. Against the
M1.3 graph median-of-run-medians, the M1.4c delta is +0.0159 ms CPU and +0.0440 ms
GPU. This is below the M1.4 +0.10 ms proxy allowance. Median normal-frame C++
allocations remain zero.

Steady live memory is unchanged at 663,553,868 B requested and 668,470,976 B
committed. The wider scene/copy formats cost no additional steady memory because the
copy now reuses expired FP16 GBuffer storage; graph-owned targets remain 663,552,000 B
requested / 668,467,200 B committed. A requested 4K capture temporarily uses an
8-byte-per-pixel (66,355,200 B) readback before CPU conversion, and remains excluded
from timing and steady-memory evidence.
