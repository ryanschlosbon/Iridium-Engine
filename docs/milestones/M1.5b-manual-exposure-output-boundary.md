# M1.5b Acceptance: Manual Exposure at the Output Boundary

- Status: Accepted
- Accepted: 2026-07-19
- Baseline: accepted M1.4 graph path on commit
  `30252593f8fdd2de5dffbb8da31bb570ff49a7c0` plus preserved dirty work
- Reference system: RTX 4090, Core i9-14900K, 64 GB DDR5, 3840x2160

## Accepted behavior

`--exposure-ev VALUE` selects a finite manual exposure in the inclusive range
[-16, 16] EV. Zero is the default. The application passes the value through the
backend-neutral initialization contract and the Vulkan output pass supplies it as a
fragment push constant. The final output shader applies `exp2(EV)` to scene-linear
ACEScg/AP1 immediately before the AP1-to-display transform. Lighting, forward
transparency, bloom input, and scene capture remain unexposed.

Invalid, missing, NaN, infinite, and out-of-range command-line values fail parsing.
The run header records the effective EV and explicitly identifies the final-output
application point. Automatic exposure remains deferred to M9.

## Verification evidence

Fresh focused Debug and Release builds passed. `ApplicationConfigTests`,
`OutputTransformConfigTests`, and `SceneColorTests` pass in both configurations.
The command-line tests cover parsing, help text, missing values, NaN, and bounds.

Debug Vulkan validation at 4K is clean with +2 EV on `opaque_emissive_v1`. Matched
Release graph runs at -2 EV and +2 EV both produced the exact pre-output PFM SHA-256
`ce5102c7cdf064d779395e94cd9640d912ab183e0a7eb5632d5935654a4f4e90`.
Their headers respectively record `manual_ev_-2.000000_applied_in_final_output` and
`manual_ev_2.000000_applied_in_final_output`. This mechanically proves that user
exposure affects only the final output path and cannot destroy scene-linear capture
range. Evidence is under `out/captures/m1.5b-exposure-*` and
`out/profiles/m1.5b-*`.

The scene-capture sidecar continues to identify `exposure: unapplied`, operator
`none`, linear AP1 primaries, full range, and the post-transparency/pre-output point.
The stale Final debug-view description was corrected to describe one final output
mapping.

## Performance and memory

Three Release runs used 4K `transparency_v1`, 200 warmup frames, and 3,000 measured
frames:

| Run | CPU frame median | GPU frame median | Output GPU median / p99 | Output CPU median |
|---:|---:|---:|---:|---:|
| 1 | 0.6484 ms | 0.470912 ms | 0.039936 / 0.043008 ms | 0.0023 ms |
| 2 | 0.6302 ms | 0.472160 ms | 0.039936 / 0.043008 ms | 0.0022 ms |
| 3 | 0.5976 ms | 0.472000 ms | 0.039936 / 0.043008 ms | 0.0020 ms |

The exposure multiply adds no measurable output-pass cost relative to M1.4's
0.0399 ms median. It remains far below the M1 0.25 ms median / 0.35 ms p99 gate;
CPU recording remains below 0.02 ms. Median normal-frame C++ allocations are zero.
Steady graph memory is unchanged at 663,553,868 B requested / 668,470,976 B
committed. Capture-readback memory is excluded from steady timing evidence.

## Acceptance and next work

M1.5b is accepted. The next slice adds direct capture of the GPU-produced final SDR
output and versioned sidecar fields that cross-reference the source scene capture,
effective exposure, operator, gamut policy, transfer, and display profile. It must
land before ACES 2 and final image baselines so those transformations can be tested
from the actual output boundary rather than a CPU-derived proxy.
