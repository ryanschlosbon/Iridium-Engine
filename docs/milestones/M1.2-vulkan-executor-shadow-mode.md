- Milestone: M1 - Render Graph, Scene-Linear HDR, and Color Management
- Slice: M1.2 - Vulkan executor in shadow mode
- Status: Accepted
- Date: 2026-07-19
- Source baseline: `30252593f8fdd2de5dffbb8da31bb570ff49a7c0` plus the preserved dirty M0/M1 worktree
- Governing plan: `docs/milestones/M1-render-graph-hdr-color.md`

## Outcome

M1.2 connects the backend-neutral compiled graph to an opt-in Vulkan shadow
executor without changing command recording or presented rendering. The legacy path
remains authoritative. `--render-graph-shadow` compiles the current maximum
deferred-plus-two-layer-transparency topology, allocates graph physical slots per
frame context, generates Vulkan barrier intents, performs an allocation-free cached
validation at frame start, and exports its topology and memory evidence in the run
header.

The accepted feature-heavy topology contains nine passes, eight logical resources,
seven engine-owned physical slots, one imported swapchain resource, and 25 barrier
intents. Two frame contexts therefore own 14 temporary shadow allocations. A source
comparison found and corrected an initial stale assumption: legacy transparency
copies the current lit scene separately for the background and foreground layers.
The accepted order is:

1. GBuffer
2. deferred lighting
3. background scene copy
4. background glass depth
5. background forward transparency
6. foreground scene copy
7. foreground glass depth
8. foreground forward transparency
9. UI and present

Empty transparency buckets remain runtime-conditional in the legacy recorder. The
shadow declaration intentionally represents the maximum fixed topology so M1.3 can
make pass enablement explicit without losing dependencies.

## Architecture and ownership

- `VulkanRenderGraphExecutor` converts abstract access states to Vulkan stage,
  access, and layout intent; holds the compiled-plan cache; and validates the active
  frame-context physical set.
- `VulkanGraphResourcePool` owns active and fence-scoped retired resource sets. A
  rebuild creates a complete candidate before retiring the old set. Allocation
  failure destroys only the candidate and preserves the active set.
- `VulkanAllocatorGraphResourceFactory` routes every shadow image/buffer through the
  central allocator under `render_graph.shadow` / `frame_context.shadow`.
- Imported swapchain state participates in the graph as external `Present -> color
  attachment -> Present` intent and is never allocated by the graph pool.
- Resize uses the existing accepted device-idle rebuild point. Shadow resources are
  destroyed and rebuilt only after candidate swapchain validation.
- Runtime allocation or validation failure disables shadow mode, records the reason,
  and leaves the legacy image path unchanged.

The state comparison against current source found equivalent Vulkan layouts and
access for color attachment, depth write/read, sampled read, transfer source and
destination, and present. Graph sampled-read stages conservatively include compute
in addition to the legacy vertex/fragment stages. Storage access has no current
legacy pass and remains a tested future mapping. Render-pass-local implicit
transitions remain legacy-owned in M1.2; M1.3 will emit the accepted graph barriers.

## Verification

The final Debug and Release builds each pass all 11 CTests. The executor-focused
binary passes 6/6 cases covering:

- abstract access and format mappings;
- exact imported/exported legacy topology;
- frame-fence-scoped retirement and device-idle cleanup;
- strong cleanup and active-set preservation under injected allocation failure;
- resolution rebuild and frame-index bounds;
- actual executor barrier generation, compiled-cache lookup, and runtime statistics.

The final 3840x2160 Debug validation run uses `transparency_v1`, which exercises both
legacy transparent layers. It reports nine passes, 25 barriers, one rebuild, zero
cache misses, and no validation messages:

- `out/profiles/m1.2-debug-shadow-transparency.jsonl`

The final visual comparison uses the same 4K fixture and measured frame with shadow
mode off and on. Both TGA files have SHA-256
`e53ab8570cc4e5e198c9a294ca06297df8ad9bead977cff32a334dd9e55aad10`.
`IridiumImageCompare` reports maximum RGBA code delta 0, zero changed pixels, and
mean/minimum luma SSIM 1.0:

- `out/captures/m1.2-final-shadow-vs-legacy.json`

This exact equality is expected because the shadow executor records no Vulkan
commands in M1.2.

## CPU, GPU, allocation, and memory evidence

Three matched Release pairs ran `transparency_v1` at 3840x2160 for 200 warmup plus
3,000 measured frames with GPU and CPU profiling. The first pair crossed a large
external clock/state transition: the legacy GPU median was 0.832736 ms while the
immediately following shadow run was 0.432608 ms. It is retained in the artifacts
but excluded from causal overhead comparison because GPU clock/power telemetry is
unavailable. Pairs two and three were stable:

| Metric | Pair 2 legacy | Pair 2 shadow | Delta | Pair 3 legacy | Pair 3 shadow | Delta |
|---|---:|---:|---:|---:|---:|---:|
| CPU frame median | 0.6757 ms | 0.7073 ms | +0.0316 ms | 0.6350 ms | 0.6422 ms | +0.0072 ms |
| Wall average | 1.012852 ms | 1.011256 ms | -0.001596 ms | 0.977456 ms | 0.982092 ms | +0.004636 ms |
| GPU frame median | 0.417888 ms | 0.417184 ms | -0.000704 ms | 0.417536 ms | 0.416736 ms | -0.000800 ms |
| Direct shadow lookup median | n/a | 0.0003 ms | +0.0003 ms | n/a | 0.0002 ms | +0.0002 ms |

The stable CPU deltas remain below the slice's 0.05 ms gate. The direct work is two
orders of magnitude below that gate and emits no GPU commands. Release retained-frame
C++ allocation-call median is zero in every legacy and shadow run. Exact artifacts
are `out/profiles/m1.2-final-{legacy,shadow}-{1,2,3}.jsonl`.

At 4K, the shadow category measures:

| Scope | Requested | Committed | Allocations |
|---|---:|---:|---:|
| One frame context | 331,776,000 B | 334,233,600 B | 7 |
| Two frame contexts | 663,552,000 B | 668,467,200 B | 14 |

This is deliberate duplicate integration memory, available only with the opt-in
flag. It is not an accepted steady renderer footprint and must be removed when M1.3
transfers ownership from legacy per-swapchain targets to graph frame contexts. The
final shadow run reports 1,658,881,868 B requested and 1,671,171,776 B committed
engine-wide versus 995,329,868 B and 1,002,704,576 B with shadow disabled; the delta
exactly equals the categorized shadow set.

## Risks and M1.3 handoff

- M1.2 generates intent but does not yet prove emitted Vulkan barriers; M1.3 owns
  command execution and validation of those barriers.
- Conditional empty transparency buckets and capture-readback insertion are not yet
  graph pass enablement. M1.3 must model them without recompiling normal frames.
- Descriptor/frame ownership is still legacy swapchain-image based. M1.3 must move
  graph-owned targets and descriptor selection together under one owner.
- The opt-in duplicate 637.50 MiB committed shadow set is temporary and may not
  survive M1.3 acceptance.
- Release whole-frame timing is sensitive to unobserved GPU clock/power state. M1.7
  still requires the planned five-run spread and external attribution.

M1.2 is accepted. M1.3 is the next authorized slice; M1 as a whole remains in
progress.
