# M4.2 Source Schema, Component Registry, Migrations, and Unknown Data

Status: Accepted on 2026-07-31.

## Delivered behavior and architecture

- Separate `IridiumSceneRuntime` and `IridiumSceneAuthoring` libraries keep source
  JSON and editor dependencies out of the runtime metadata boundary.
- Strong stable component/property IDs and explicit four-byte cooked section IDs.
- Frozen, deterministic runtime/source registries with injected callbacks, exact
  five-component manifests, property defaults/nullability/reference kinds, source
  field bindings, and contiguous one-version migration chains.
- Strict bounded JSON parsing rejects BOMs, syntax errors, trailing content,
  comments, non-finite numbers, and duplicate keys before DOM acceptance.
- Schema-1 semantic validation covers canonical UUIDv5/v7 entity identity, known
  property types/default/null contracts, future versions, duplicate components,
  hierarchy references/cycles/sibling order, asset/subasset UUIDv7 references, and
  unique canonically ordered material overrides.
- Canonical two-space/LF/final-newline output uses hierarchy preorder, registered
  component/property order, deterministic unknown-field order, and byte-stable
  repeated round trips.
- Unknown components, properties, component-envelope members, and top/entity
  extensions survive semantic round trips. Unknown component versions remain opaque;
  future versions of known components fail safely.
- Pure logical-v0 migration derives scene UUIDv5 values from scene asset identity,
  migrates Name/Transform/Relationship/Mesh/material overrides/Light, validates
  redundant hierarchy fields, preserves unknown legacy entity fields, and hard
  rejects every tracked path-identity predecessor.
- Scene UUID implementation is self-contained in the runtime scene library; it no
  longer inherits the asset library's JSON linkage.

The current editor `SceneSerializer` remains the production fallback as planned.
M4.3 owns staged active-document commit, atomic save/recovery, and switching editor
Open/Save/Save As to this accepted representation.

## Interfaces and files

- Runtime identity/metadata: `src/scene/SceneEntityUuid.*`,
  `src/scene/runtime/ComponentIdentity.*`, `RuntimeComponentRegistry.*`,
  `CoreComponentRegistry.*`, and `SceneDiagnostic.*`.
- Authoring: `src/scene/authoring/SourceJsonParser.*`,
  `SourceComponentRegistry.*`, `CoreComponentCodecs.*`,
  `SourceSceneDocument.*`, and `SourceSceneEnvelopeMigrator.*`.
- Tests: runtime/source/core registry, strict parser, canonical document, and v0
  migrator executables under `tests/scene/`.
- Scale evidence: `tools/SourceSceneBenchmark.cpp` and
  `docs/performance/M4.2-source-scene-scale-2026-07-31.md`.

## Performance and visual comparison

Canonical 100k serialization is 481.971 ms p95 versus the M4.0 v0 save's
1,809.439 ms. Strict 100k parse/validation is 8,610.990 ms p95 versus the
transitional v0 load's 1,450.162 ms. The slower strict path is accepted as an
explicit M4.3 optimization risk, not a production runtime path; cooked scenes remain
the runtime solution. Full details and limitations are in the performance report.

No renderer code, frame timing, VRAM behavior, or expected image changed. Vulkan
capture reruns are therefore not required for this source-schema-only slice.

## Remaining risks and deferred work

- High source-DOM allocation pressure at 100k entities; M4.3 must measure staged
  open/commit and remove avoidable copies before considering streaming complexity.
- Core callbacks are injected at composition boundaries. Their production Registry
  adapters arrive with staged loading/editor separation, avoiding a temporary
  runtime dependency on current ImGui-coupled component headers.
- Atomic files, active-scene rollback, editor lifecycle, and recovery are M4.3.
- Cooked runtime scene encoding/loading is a later planned slice.

No ADR changed: this slice implements the accepted M4 plan and ADR-0004 boundaries.
