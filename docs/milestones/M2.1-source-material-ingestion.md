- Status: Complete on 2026-07-22

## Decision

M2.1 is complete. Iridium now has one provenance-preserving CPU material ingestion
entry point for textual glTF and GLB. It produces a read-only `SourceMaterialDocument`
whose materials retain stable import-local indices, glTF values and defaults,
authored/default origin, texture-use semantics, channel and transfer interpretation,
UV selection and texture transforms, source samplers, alpha/culling state, supported
extension data, and `KHR_materials_variants` mappings. Structured diagnostics use
stable severity, code, and JSON path fields.

The renderer still uses fastgltf and the legacy `MaterialAsset` at runtime. That is
the deliberate M2.1 rollback boundary. The M0 material-diagnostic sidecar no longer
has an independent JSON parser: it is projected from `SourceMaterial`. M2.2 consumes
the same source document for compilation; M2.4 later activates compiled materials in
the renderer.

Renderer, RHI, Vulkan, shaders, GBuffer formats, lighting, and frame scheduling did
not change.

## Implemented contract

- `SourceMaterialDocument` owns source data and exposes only const spans. A material
  records core metallic/roughness inputs, emissive, normal/AO strength, alpha mode and
  cutoff, double-sided state, all texture uses, and extension records.
- Texture interpretation belongs to each use. An image reused by base color and
  metallic/roughness therefore retains separate sRGB and linear interpretations.
- Texture uses record core and supported extension channels, image identity, UV set,
  `KHR_texture_transform`, and glTF sampler defaults or authored filter/wrap values.
- Supported M2 source extensions are emissive strength, IOR, specular, clearcoat,
  sheen, anisotropy, iridescence, transmission, volume, dispersion, diffuse
  transmission, unlit, and archived specular/glossiness. Their authored payload and
  defaulted properties are retained. Texture transforms and material variants are
  represented in their owning texture/primitive domains.
- Unknown optional extensions are preserved canonically and warned. Unknown required
  extensions, invalid indices, invalid ranges, missing required UV streams, invalid
  sampler values, and malformed GLB/JSON produce deterministic errors.
- Variant names and primitive-to-material mappings retain import-local indices; M3/M4
  still own durable identity and serialized selection.

The existing M0 fixture contains an out-of-schema emissive factor of 2.0. The M2
document correctly emits `GLTF_FACTOR_RANGE`. The temporary M0 projection keeps that
fixture inspectable and surfaces the error as a warning instead of rejecting the old
diagnostic snapshot. Strict compilation in M2.2 rejects it. This compatibility rule
is confined to `MaterialProvenance` and is not part of the source or compiler contract.

## Automated verification

Complete Debug and Release builds succeed. Each configuration passes all 16 CTests.
The new `SourceMaterialTests` covers:

- core defaults versus authored values;
- texture channels, transfer roles, UV selection, transforms, sampler defaults and
  authored sampler state;
- one image used simultaneously in sRGB and linear roles;
- all thirteen supported material-extension records and their format defaults;
- unknown required extensions, invalid texture indices, and stable diagnostic codes;
- GLB JSON-chunk ingestion through the same material path;
- material variants and missing-UV diagnostics;
- factor range rejection;
- the optional licensed car aggregate snapshot.

The car snapshot passes with 87 materials, 25 default metallic values, 61 authored
zero metallic values, five BLEND materials, 72 normal textures, two
metallic/roughness textures, one occlusion texture, no emissive textures, and no
nonzero emissive factors. Paint, window, and transmissive-lens indices retain the
extension and alpha facts frozen by the M2 audit.

`MaterialProvenanceTests` also passes unchanged in behavior, showing that M0 facts,
runtime snapshots, and fallback diagnostics now come through the new source document.

## Import-time performance and allocation evidence

`SourceMaterialBenchmark` is a Release import benchmark. It performs two warm-up and
ten measured iterations. Allocation counts cover C++ global `new`/`new[]` calls and
requested bytes only; they do not claim third-party allocator internals or driver
memory.

| Source | Median | p95 | Mean allocations | Mean requested bytes |
|---|---:|---:|---:|---:|
| 10,000 factor-only materials | 52.573 ms | 55.665 ms | 490,120 | 34,292,611 B |
| Licensed sample car, 87 materials | 5.468 ms | 7.249 ms | 31,817 | 3,405,355 B |

This is import/change-time work and adds no steady-frame execution or GPU resource.
The allocation volume is acceptable for the first correctness slice but is a clear
cooking/import optimization opportunity; M2 does not treat these figures as a
steady-state budget precedent.

## Rollback and remaining risks

The old fastgltf-to-`MaterialAsset` renderer path remains active, so the new module
can be disconnected without changing rendering. No accepted ADR changed in this
slice.

Remaining work is intentionally assigned to later M2 slices:

- M2.2 must turn source records into standard, complex, or unlit closure recipes and
  reject strict source errors without silent repair.
- M2.3 separates compiled materials, instances, and packed GPU records.
- M2.4 activates the compiled standard path and resolves runtime agreement with the
  temporary fastgltf material path.
- M3 owns stable asset identity, cooking, derived data, texture products, and durable
  variant selection.

The next slice is M2.2: pure compiler and canonical closure math. It remains CPU-only
and renderer-inactive until its equation, classification, diagnostic, determinism,
and performance gates pass.

Post-acceptance evidence note: M2.2 corrected the validation rule for
`KHR_materials_volume.thicknessFactor` from `[0,1]` to finite and nonnegative, matching
the extension contract. No M2.1 fixture result or renderer behavior changed.
