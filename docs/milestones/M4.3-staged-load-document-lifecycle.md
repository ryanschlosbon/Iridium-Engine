# M4.3 Acceptance: Staged Load and Editor Document Lifecycle

- Status: Accepted on 2026-08-01
- Parent plan: `docs/milestones/M4-scene-schema-ecs-editor-separation.md`
- Performance evidence: `docs/performance/M4.3-scene-document-lifecycle-2026-08-01.md`
- Next slice: M4.4 deterministic cooked runtime scenes

## Accepted behavior and architecture

`SceneWorld` load is a multi-phase transaction. It creates every entity and UUID
mapping, decodes registered components, records and resolves stable references,
reconstructs hierarchy, runs fixup/post-load validation, and commits only by
swapping a complete staging world into the address-stable application-owned world.
Any failure leaves the active world untouched.

The editor document service is now the sole production source-scene owner. It owns
the current path and scene sidecar identity, semantic document, diagnostics,
state-token save checkpoint, schema-0 migration, Save/Save As, atomic replacement,
backup and crash-temporary recovery, and world/source capture. `SceneSerializer`
has no production call site and remains compiled only as a characterization
comparator until its planned removal.

File-menu operations call the dedicated `EditorSceneDocumentActions` command layer.
The same commands used by the visible menu have automated coverage for canonical
path adoption, failed-open retention, Open, backup recovery, temporary recovery,
and persistent-UUID selection remapping. ImGui owns presentation only; it does not
own scene state or transaction policy. Orphan discovery hashes exact destination-
specific sibling temporaries asynchronously and never promotes or deletes one
without an explicit recovery command.

Name, Transform, Relationship, Mesh, and Light use frozen registry adapters rather
than a serializer switch. Live capture retains unknown envelope/entity/component/
property payloads and serializes stable UUID/GUID intent only. Pending, failed,
evicted, and later-resident runtime asset state does not alter the history token,
dirty state, or saved model/material override GUIDs.

Automated failure coverage includes strict parse and migration failure, duplicate/
invalid identities, required and optional references, hierarchy cycles, component
fixup/post-load failure, atomic create/write/flush/verify/replace faults, sidecar
rollback, corrupt primary/backup/temp behavior, and failed operation retention of
world/path/checkpoint/selection state.

The 1,000-frame Release 3840x2160 material-lab run used the accepted cooked model,
the Khronos validation layer, 500 warmup frames, and source import of zero. It
reported zero dropped frames and no VUID/validation message. CPU editor build was
0.0699 ms median, 0.2070 ms p95, and 0.3241 ms p99; total CPU frame was 2.9023 ms
median and GPU frame was 0.3883 ms median. Steady C++ allocation median remained
zero. These numbers validate integration behavior, not a new renderer baseline.

Five independent Release startup runs report editor initialization values of
0.0206, 0.0207, 0.0214, 0.0221, and 0.0211 ms: 0.0211 ms median versus the accepted
M3 0.0537 ms median (-60.7%). The unchanged 30-sample 100k inspector construction
case is 84.992 ns/op median with zero allocations, improving on M4.1's 89.908 and
M4.0's 130.111 ns/op medians. Its 100.499 ns/op p99 is effectively unchanged from
M4.1's 100.445 ns/op.

At 100k entities, validated stage is 367.181 ms median, live capture is 321.195 ms,
and active-world commit is 0.0008 ms with zero allocations. Verified atomic source
save is 20.019 s and strict parse is 18.627 s median. Those source-authoring costs
are accepted as an explicit large-JSON risk, not a runtime target. M4.4's cooked
binary scene is the production-scale solution.

## Visual, performance, and compatibility disposition

M4.3 changes no renderer, shader, RHI, material closure, color, output transport,
primitive, or GPU resource contract. No expected image or renderer performance
baseline changed, and no visual or VRAM improvement is claimed. The 4K validation
run preserves the accepted material-lab draw/material topology and source-free
cooked model startup.

The M3 GUID, subasset, material override, pending-residency, sidecar, and cooked-only
runtime contracts remain intact. Save As preserves entity UUIDs and creates a new
scene-asset UUIDv7 sidecar. All known path-identity predecessor fields remain hard
migration diagnostics.

## Remaining risks and next slice

- Very large source JSON is slow and allocation-heavy. Validation and rollback are
  not weakened; M4.4 owns deterministic compact cooked scenes.
- The old serializer is still compiled for characterization. It is not a fallback
  writer and is removed only at the planned production-cleanup slice.
- Runtime components still contain editor inspector hooks. M4.5 owns that separate
  runtime/editor component cleanup after cooked scenes are established.
- Undo/redo and structural editing remain M4.6/M4.7 work; the M4.3 state token is
  the checkpoint contract those slices consume.

No ADR changed. M4.3 follows the already accepted M4 architecture and advances M4.4.
