## Frozen color contract

### Reference implementation

- Production transform: ACES 2 core Output Transform.
- Frozen package: official ACES release `v2.0.0+2025.04.04`, not the moving `main`
  branch: `https://github.com/aces-aswf/aces/releases/tag/v2.0.0%2B2025.04.04`.
- Reference code license: Apache-2.0. Preserve required attribution for any ported
  constants or algorithms.
- Implementation strategy: port the parameterized core algorithm and validate it
  against the tagged CTL reference vectors. Do not bake one opaque LUT or copy a
  third-party approximation.
- Scene working space: linear ACEScg/AP1 with the ACES white point. Source sRGB and
  Rec.709 inputs are decoded and transformed into AP1 before lighting.
- The production operator converts the AP1 scene value through the tagged ACES input
  and rendering transform and returns display-linear values in the target gamut.
  Display encoding remains separate so UI can be composed before the final transfer.
- Compatibility operator: the current fitted `ACESFilm` curve, named
  `AcesFittedLegacy`. It obeys the same display-linear output contract.
- Diagnostic operator: identity/clamp, never a production default.

### Output configuration

The backend-neutral configuration owns values, validation, serialization, and user
settings. The Vulkan backend owns surface formats, color spaces, extension functions,
swapchain rebuilds, and HDR metadata calls.

`OutputTransformConfig` must contain:

- operator, output transport, and output-profile identity;
- target/encoding RGB chromaticities and white point;
- transfer function and reference/peak luminance;
- manual exposure EV and UI paper-white luminance;
- optional mastering minimum, MaxCLL, and MaxFALL metadata;
- the frozen ACES package/tag and exact transform/preset identity;
- explicit effective values after capability and range validation.

Frozen user bounds/defaults:

| Setting | Default | Validated range/behavior |
|---|---:|---|
| Manual exposure | 0 EV | -16 to +16 EV; persisted; captured |
| HDR UI paper white | 203 nits | 80 nits through effective peak; persisted |
| HDR target/mastering peak | 1,000 nits | paper white through 10,000 nits; persisted and capability-clamped where required |
| Mastering minimum | unknown | serialize 0 when unknown; never invent a panel black level |
| MaxCLL / MaxFALL | unknown | serialize 0 when unknown; user/measurement override only |
| scRGB luminance scale | 80 nits per 1.0 | fixed Windows transport definition; paper white 203 nits encodes as 2.5375 |

Invalid NaN/infinite values are rejected. Invalid persisted values fall back to the
defaults with a diagnostic; they are not silently propagated into shaders or Vulkan
metadata. SDR uses a nominal 100-nit rendering target and normalized UI white; HDR
paper-white controls do not pretend to set physical SDR monitor luminance.

### Initial output profiles

| Profile | Rendering target | Encoding/transport | M1 requirement |
|---|---|---|---|
| Windows SDR sRGB | Rec.709, D65, 100 nits | Rec.709/sRGB piecewise through `B8G8R8A8_SRGB` | Required default and fallback |
| Windows scRGB | P3-D65 limiting gamut at effective user peak | Linear extended Rec.709 basis, FP16, 80 nits per 1.0 | First HDR path |
| HDR10 | P3-D65 limiting gamut at effective user peak | Rec.2100/Rec.2020 container, ST.2084 PQ, 10-bit | Required where exposed |

Display-P3 (D65 consumer display) and cinema DCI-P3 are distinct future profiles.
Their primaries, white points, transfer functions, and luminance assumptions must not
be aliased. Adding either must not change the AP1 scene, lighting shaders, graph
resource contracts, or capture-domain definitions.

## Capability inventory

### Vulkan and engine state

- Loader/device API: Vulkan 1.4.341 / 1.4.341.
- Reference GPU: NVIDIA GeForce RTX 4090, driver 610.74, UUID
  `3e45ec9c96fc398d79613146f37d826d`.
- Loader advertises `VK_EXT_swapchain_colorspace` revision 4.
- RTX 4090 advertises `VK_EXT_hdr_metadata` revision 3.
- Current `VkContext` requires/enables only `VK_KHR_swapchain`; it does not enable
  either HDR-related extension.
- Current `VkSwapchain` chooses only
  `VK_FORMAT_B8G8R8A8_SRGB` + `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR`, then falls back to
  the first reported pair. It has no output-mode request or capability diagnostic.
- The accepted M0 Release run header confirms 3840x2160, three-image Mailbox,
  `B8G8R8A8_SRGB`/sRGB nonlinear, legacy fitted-ACES-in-lighting, native resolution,
  no reconstruction, and Release build provenance.
- Extended surface-format/color-space pairs are `unavailable` in this preflight.
  M1.6 must enable the instance extension before enumeration, record every pair, and
  use exact pair negotiation with an explicit SDR fallback.

### Windows display state

The 2026-07-19 hidden DxDiag inventory records two active 4K displays:

| Display | Mode | Windows color state |
|---|---|---|
| Alienware AW3225QF | 3840x2160 at 240 Hz | HDR supported and enabled; `RGB_FULL_G2084_NONE_P2020`; measured descriptor primaries recorded by DxDiag |
| Kamvas Pro 24 | 3840x2160 at 60 Hz | HDR supported but Advanced Color not enabled; `RGB_FULL_G22_NONE_P709` |

Target-display HDR validation must place the window center on the AW3225QF and record
its identity, mode, Advanced Color state, selected Vulkan pair, and effective output
settings. Window movement between displays is an output-capability change and must
trigger re-evaluation/rebuild or a documented SDR fallback; validation may not assume
the primary/first enumerated monitor.

## M1.6 prerequisites discovered

- Add optional instance-extension negotiation for `VK_EXT_swapchain_colorspace`.
- Add optional device-extension negotiation and function loading for
  `VK_EXT_hdr_metadata`.
- Query and serialize all surface format/color-space pairs and exact rejection
  reasons.
- Represent requested versus effective output mode separately.
- Rebuild output resources on monitor/mode/profile changes and invalidate history.
- Keep HDR metadata optional and distinct from the selected color space/encoding;
  metadata never overrides transport negotiation.
