- Status: Accepted on 2026-07-31
- Parent plan: `docs/milestones/M4-scene-schema-ecs-editor-separation.md`
- Performance evidence:
  `docs/performance/M4.1-generational-identity-2026-07-31.md`

## Accepted result

Runtime entity identity is now stale-safe and distinct from persistent scene
identity.

- `EntityHandle` is a strong 64-bit index/generation value with an explicit
  logical-v0 index adapter. Destroyed handles cannot access recycled slots.
- `Registry` owns generation, alive, and free-list state; rejects null/dead/stale
  handles; makes pool discovery non-mutating; and treats generation exhaustion as a
  hard non-destructive error.
- Dense component storage is retained. Sparse maps use a 32-bit slot index and
  validate the full handle stored at the dense slot.
- `SceneEntityUuid` accepts non-nil RFC UUIDv5/v7 only. UUIDv7 is used for new
  entities and UUIDv5 is available for deterministic migration derivation.
- `SceneIdentityMap` provides checked forward/reverse bindings and consistency
  diagnostics. `SceneWorld` owns it with the Registry and makes identity assignment
  and removal part of entity creation/destruction.
- `Application` now owns one `SceneWorld`; existing Registry call sites pass through
  its observer, so every production scene entity receives a persistent UUID.
- Transform hierarchy evaluation treats a stale recycled-parent handle as invalid
  rather than allowing it to alias the replacement entity.
- The old serializer remains operational only through explicit logical-v0 handle
  conversion. It does not define the new source schema; M4.2 does.

## Performance and visual comparison

Dense Transform iteration is +1.9% p95 and large mixed creation is +3.9%. Legacy-v0
save/load are +2.3%/+4.4%. Component hit/view/sort paths improve substantially after
the index-key/full-handle-validation sparse-map correction. Expected costs remain in
creation/recycle state, 64-bit hierarchy snapshots, random misses, breadth traversal,
and selection lookup; exact values and allocation attribution are in the linked
performance report.

The stale probe rejects one million recycled handles in 1.766 ms p95. Creating and
binding one million deterministic UUIDv7 identities costs 586.620 ms p95 and
152.77 MiB of operation-local requested allocation. Identity has no steady-frame
allocation.

M4.1 contains no renderer or shader change and replaces no image baseline. The
representative runtime remains validation-clean.

## Remaining risk and deferral

- The current source serializer still persists transient logical-v0 IDs and retains
  its characterized loss/atomicity defects. M4.2/M4.3 replace that path.
- UUIDv5 migration must be namespaced by the scene asset sidecar GUID plus legacy
  entity ID; it must never use a source path.
- 64-bit structural snapshots and generation-validated miss/selection paths remain
  explicit M4.8 optimization candidates.
- The cooked runtime scene format remains deferred to M4.4.

No ADR changed. `ROADMAP.md` remains M4 `In Progress`; M4.1 is accepted and M4.2 is
active.
