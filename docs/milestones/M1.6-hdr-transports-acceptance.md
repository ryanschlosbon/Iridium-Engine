# M1.6 Acceptance: scRGB, HDR10/PQ, and HDR Metadata

- Status: Accepted
- Date: 2026-07-22
- Reference system: RTX 4090, driver 610.74, Vulkan 1.4.341, Windows 11 25H2
- Source baseline: `30252593f8fdd2de5dffbb8da31bb570ff49a7c0`, dirty worktree preserved

## Accepted implementation

The Vulkan backend now negotiates an exact format/color-space pair and records both
requested and effective transport. SDR remains the mandatory fallback. scRGB uses
`R16G16B16A16_SFLOAT` plus `EXTENDED_SRGB_LINEAR`; HDR10 uses
`A2B10G10R10_UNORM_PACK32` plus `HDR10_ST2084`. The reference surface exposes all
three pairs and `VK_EXT_hdr_metadata`.

The common Academy ACES 2 P3-D65 1000-nit/Rec.2100-PQ LUT produces the HDR rendering
transform. scRGB decodes PQ to absolute Rec.2020 luminance, converts to extended
linear sRGB, and applies the Windows 80-nit-per-unit scale after UI composition.
HDR10 retains linear Rec.2020 through a graph-owned FP16 UI-composition target and
encodes ST.2084 only in the final present pass. UI colors are decoded from authored
sRGB, converted to the target primaries, and placed at configured paper white before
transport encoding. PQ code-space blending is not used.

`--paper-white-nits` defaults to 203 and `--peak-nits` to 1000. Both are validated
and serialized; output constants enforce the configured luminance ceiling. HDR
metadata uses P3-D65 mastering primaries, the configured peak,
and zero for unknown mastering minimum/MaxCLL/MaxFALL instead of inventing panel
measurements. Non-ACES compatibility operators are rejected for HDR transports.

HDR final captures are FP32 PFM linear references relative to paper white. Their
sidecars identify Rec.709/scRGB or Rec.2020/HDR10 primaries, transport, transfer,
ACES transform, paper white, and peak. The profile header records the same values and
whether HDR metadata was actually applied.

## Verification

- Debug and Release: 15/15 CTests pass. Focused tests cover exact transport tables,
  extension/fallback behavior, SDR/scRGB/HDR10 graph topologies, ST.2084 reference
  vectors, Rec.2020/scRGB conversion, configuration bounds, and HDR sidecars.
- Vulkan validation: clean at 3840x2160 for all six required M0 fixtures and the
  M1 color-volume fixture in SDR, scRGB, and HDR10. Targeted scRGB/HDR10 resize,
  rebuild, and normal-close runs are also clean. Evidence is under
  `out/evidence/m1/m1.7-validation/` and `m1.7-resize/`.
- The three 4K scene-linear captures are byte-identical, SHA-256
  `fbda36388bac4884ca3394494d812b50de412f9d8ac268608863633193eb9515`.
  This proves output transport does not feed back into scene composition.
- Final HDR references are finite. The scRGB reference spans
  `-0.0013914108..4.05078125` units, retaining legal extended-gamut negative values;
  HDR10's linear Rec.2020 reference spans `0.0016689301..3.634765625` paper-white
  units. Inspected previews preserve the grayscale steps, saturated colors,
  highlight range, and transparent overlap.
- A 400-nit HDR10 capture peaks at 1.9697265625 paper-white units, below the exact
  `400/203 = 1.97044335` ceiling after FP16 quantization. This proves the user peak
  affects output constants as well as metadata.
- Windows compositor captures at -4/+4 EV preserve identical UI patch codes in each
  transport while a scene sample changes from `(6,6,6)` to `(255,255,255)`. scRGB
  patches are `(101,101,101)`, `(195,195,195)`, white, R, G, B; HDR10 differs only
  by one gray code and four green-channel codes after compositor mapping. Evidence:
  `out/evidence/m1/m1.7-target-display/`.
- Nsight Graphics 2026.2 command-line Graphics Capture and GPU Trace were retried
  with its local monitor running but emitted no new artifact. This is not counted as
  evidence. Existing M0/M1.5 externally attributed timestamp/debug-marker machinery
  is unchanged; the existing `gpu.ui` boundary was kept around UI only and the new
  HDR encode work has its own `gpu.output.hdr10_encode` range.

## Performance and memory

The frozen Release protocol was used at 4K: five runs per transport, 500 warm-up and
10,000 measured frames, validation off, GPU timestamps on. Medians below are the
median of five run medians.

| Transport | Output transform | UI | Final encode | Total output/UI | GPU frame | CPU frame |
|---|---:|---:|---:|---:|---:|---:|
| SDR | 0.043008 ms | 0.101376 ms | fixed-function | 0.144384 ms | 0.421312 ms | 0.563500 ms |
| scRGB | 0.049152 ms | 0.217088 ms | scale in UI | 0.266240 ms | 0.546400 ms | 0.930600 ms |
| HDR10 | 0.049152 ms | 0.098304 ms | 0.058368 ms | 0.205824 ms | 0.485888 ms | 0.787500 ms |

The HDR transform delta versus SDR is 0.006144 ms for scRGB and HDR10, below the
0.05 ms transport-transform gate. HDR10's separately attributed full-screen PQ
encode costs 0.058368 ms. Every path remains far below the 0.8 ms combined budget;
the output transform p99 is at most 0.050176 ms for scRGB and 0.049152 ms for HDR10,
well below 0.35 ms. Steady C++ allocation median remains zero.

| Transport | Engine requested peak | External swapchain estimate | Total requested peak | Engine committed peak |
|---|---:|---:|---:|---:|
| SDR | 797,021,720 B | 99,532,800 B | 896,554,520 B (855.021 MiB) | 802,430,416 B |
| scRGB | 730,666,520 B | 199,065,600 B | 929,732,120 B (886.662 MiB) | 735,583,696 B |
| HDR10 | 730,666,520 B | 99,532,800 B | 830,199,320 B (791.740 MiB) | 735,583,696 B |

All remain below the M0 949.220 MiB requested gate. FP16-compatible graph lifetimes
reduce scRGB/HDR10 to six physical slots. HDR10's UI-composition image reuses an
expired compatible slot, so it adds no steady engine allocation. Repeated resize
runs report no growing allocations or validation errors.

## Disposition

M1.6 is accepted. SDR is the default and mandatory fallback; scRGB is the approved
first HDR path; HDR10/PQ and optional metadata are implemented and validated on the
reference surface. Display-P3 and cinema DCI-P3 remain later profiles, not aliases
for either Windows SDR or HDR10.
