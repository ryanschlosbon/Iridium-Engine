# M0.1 Measurement Contract and Current-System Inventory

- Milestone: M0 - Reference Scenes and Profiling Foundation
- Slice: M0.1 - Inventory and measurement contract
- Status: Accepted
- Date: 2026-07-17
- Baseline commit: `30252593f8fdd2de5dffbb8da31bb570ff49a7c0`
- Baseline branch: `Render-Refactor-for-Modularity`
- Related records: ADR-0001 through ADR-0005

## Outcome

This document freezes the names, units, ownership, frame association, availability,
and collection rules for M0 telemetry. It also records the current renderer
inventory, reference-content constraints, benchmark protocol, and baseline
preflight evidence.

M0 instrumentation must report what the current engine actually does. It must not
present requested draws as executed draws, committed allocations as resident VRAM,
display-referred images as scene-linear data, or unavailable counters as zero.

## Current frame and resource inventory

### Frontend frame flow

`Application` owns event polling, input, asset swaps, transform updates, editor UI
construction, render extraction, queue sorting, and calls to the high-level RHI
backend. It produces one 112-byte `DrawPacket` per merged material submesh and
repeats the entity world matrix in every packet.

Opaque packets are sorted by pipeline/material identity. Transparent packets are
sorted by distance from the camera to the entity origin. This distance is not a
primitive bound or depth interval.

### Backend frame flow

`VulkanVertexBackend` records the current manual pass sequence:

1. flush pending uploads;
2. wait/reuse a two-frame scheduler context and acquire a swapchain image;
3. GBuffer opaque draws and optional selection mask draws;
4. deferred lighting and selection outline;
5. legacy transparent background copy/depth/forward work;
6. legacy transparent foreground copy/depth/forward work;
7. ImGui/UI rendering;
8. queue submission and presentation.

The transparent background bucket contains every transparent packet except the
last; the foreground bucket contains the last packet. These are legacy submission
buckets, not physical layer classification.

### Frame synchronization

`VulkanFrameScheduler` owns two frame contexts. Each has a command pool, command
buffer, image-available semaphore, fence, and deferred-deletion queue. Present-wait
semaphores are per swapchain image. `beginFrame` waits for the frame-context fence,
may wait for a prior image owner, and performs an infinite-timeout acquire. These
existing waits are measured workload behavior; instrumentation must not add another
wait to obtain results.

GPU query pools will be frame-context-owned. Results are read only after the owning
frame fence has completed, using availability data and never
`VK_QUERY_RESULT_WAIT_BIT`. An unavailable or overflowed sample is dropped and
counted rather than blocking.

### Uploads

`VulkanUploadContext` uses a separate graphics command buffer and a blocking fence
wait when a batch is flushed. It owns staging buffers until that wait completes.
Upload bytes, batch counts, and CPU wait time are required. GPU upload duration is
optional until the upload context has its own safe query ownership; it must not be
folded silently into the main graphics-frame duration.

### Resources and memory

`VulkanResourceAllocator` currently performs one `VkDeviceMemory` allocation per
buffer or image and does not track live allocations. The allocation requirement is
known at creation time, which is the source of truth for engine-committed bytes.

At 4K, each current swapchain-image target set contains three `RGBA16F` GBuffer
targets, two `D32` targets, and three swapchain-format color images including the
external swapchain image. Engine-owned committed allocation bytes, driver heap
usage/budget, and external swapchain ownership are separate scopes.

There is no render graph yet. Current per-image targets are labelled
`persistent.legacy_per_image`; no data is reported as transient or aliased.

## Stable telemetry contract

### Common rules

- Serialized names are stable UTF-8 dotted names. Runtime implementations may
  intern them to fixed IDs.
- Durations are unsigned integer nanoseconds. Memory is bytes. Rates are derived,
  never stored as ambiguous counters.
- Every submitted frame has a monotonically increasing 64-bit frame ID. Delayed
  GPU results retain the ID of the frame that recorded them.
- CPU events record thread ID, start, duration, parent event, and availability.
- GPU ranges record name, duration, queue, frame ID, and availability.
- Counter scope is explicit: requested, recorded, submitted, estimated, optional,
  or unavailable.
- Completed-frame storage and per-thread event storage are bounded. Overflow drops
  new detail, increments an overflow counter, and preserves the rest of the frame.
- Median, p95, and p99 use nearest-rank percentiles over available samples. Reports
  include sample and missing-sample counts.
- Collection-disabled code must not allocate and must have measured overhead.

- `buffer.uniform`
- `buffer.upload_staging`
- `image.texture`
- `image.environment`

Each record carries requested bytes where meaningful, committed allocation bytes,
memory type/heap, lifetime class, and live/peak state. Optional

allocation totals.

## Machine-readable run schema

The M0 export is versioned JSON Lines. The first record is a `run_header`; later
records are `frame` records. A final `run_summary` contains aggregation and missing
sample counts.

The run header includes at minimum:

- schema version and run ID;
- commit, branch, dirty state, build configuration, compiler, and shader compiler;
- OS, CPU, memory, GPU name/UUID, driver, Vulkan API/SDK, and active layers;
- resolution, base resolution, reconstruction mode, output mode, swapchain format,
  color space, present mode, and validation state;
- fixture ID/revision/content hashes, camera ID/path, quality settings, and render mode;
- warm-up, measured frame count, cache state, and profiler feature flags;
- capture color domain, exposure state, and current output operator.

Each frame record includes frame ID, CPU events, delayed GPU ranges, counters,
allocation deltas/totals, overflow flags, and unavailable-field diagnostics.

Exact source JSON, output images, and heatmaps are separate files referenced by
relative path and content hash; large binary data is not embedded in telemetry.

## Reference-content and deterministic-run contract

### Required redistributable fixtures

Acceptance fixtures must be tracked, procedural, or have a recorded license that
permits repository use and redistribution. M0 will use small procedural geometry
and purpose-built textures where possible rather than introduce M3's future asset
registry prematurely.

Benchmark definitions use an M0-only versioned manifest containing fixture ID,
content revision, scene factory or source path, camera, resolution, output label,
quality settings, warm-up, run length, and expected qualitative behavior. This is
not the future M4 scene schema and must not acquire general scene-serialization
responsibilities.

The current camera is interactive and not serialized. Benchmark cameras therefore
come from the manifest or a deterministic camera path, never from the editor's last
interactive state.

### Performance run protocol

Unless a benchmark explicitly documents a different requirement:

1. build with `x64-release`;
2. disable Vulkan validation and unrelated overlays for performance runs;
3. require and record the reference GPU UUID rather than trusting enumeration order;
4. render at an actual 3840x2160 target, not a scaled editor viewport;
5. use fixed fixture, camera/path, output mode, present mode, and shader/cache state;
6. warm for at least 500 frames and until shader/resource creation has settled;
7. measure at least 10,000 frames for the initial percentile baseline;
8. report median, p95, p99, sample count, missing samples, and run-to-run spread;
9. record cold import/upload separately from warm steady-state rendering;
10. capture display-referred output and any genuinely available intermediate in
    separately identified color domains.

Instrumentation-overhead tests interleave disabled and enabled runs across at least
five repetitions. Disabled overhead must not exceed 0.05 ms or 1% median CPU-frame
time, whichever is larger. Enabled core-marker overhead must not exceed 0.10 ms or
2%; p99 impact is reported separately. Exceeding a threshold reopens the data
structure or collection strategy rather than being waived silently.

## Current color and debug-view limitations

The current lighting shader tone-maps into a swapchain-format sRGB image before
transparency. Glass samples that display-referred copy and separately tone-maps its
environment reflection. M0 records this as
`legacy_display_referred_srgb_target`; it does not claim a full scene-linear
capture. Correct scene-linear HDR composition belongs to M1.

Available editor modes are Standard, Wireframe, and Glass Depth. Base color,
metallic, roughness, normals, emissive, and opaque depth exist as internal targets
or channels but are not yet exposed as debug views. Material ID and motion vectors
do not exist and are reported as unavailable.

The GBuffer implementation has three `RGBA16F` color targets. Shader comments that
describe two targets or 96 bits are stale and must not drive accounting.

## Ownership and integration

The milestone lead owns changes to `IRenderBackend`, frame telemetry contracts,
`Application`, `VulkanFrameScheduler`, `VulkanVertexBackend`, allocator/upload
accounting, frame-target capture transitions, and central CMake integration.

After these interfaces are frozen, disjoint work may prepare fixtures, provenance
tests, image-comparison tooling, aggregation/export tests, and external-profiler
cross-checks. Write-heavy changes to scheduler/backend headers, central build files,
shader interfaces, or material structures must not run concurrently.

## M0.1 completion assessment

- Desired metrics are mapped to owners, units, source APIs, and availability.
- GPU result collection adds no unexplained global wait.
- The RHI exposes completed backend-neutral telemetry, not Vulkan query objects.
- Current reference-asset locations, hashes, and licensing gaps are recorded.
- Deterministic camera and benchmark-manifest strategy is defined without taking on
  M3/M4 architecture.
- Stale review findings and current build/environment prerequisites are recorded.
- Debug and Release builds/tests pass, and the current Debug Vulkan smoke produced
  no validation output.

M0.1 is accepted. M0.2a is the only implementation slice authorized to be in
progress next.
