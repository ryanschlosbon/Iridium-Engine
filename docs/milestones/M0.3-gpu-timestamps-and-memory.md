## Outcome

M0.3 adds backend-owned Vulkan timestamp pools to each of the two frame contexts.
Collection resets and writes queries in the owning command buffer. Results are read
only after that frame context's existing fence wait, with 64-bit values plus
availability and without `VK_QUERY_RESULT_WAIT_BIT`. Unavailable and overflowed
ranges are retained as unavailable diagnostics and counted; no result path adds a
normal-frame wait.

Completed GPU ranges are attached to the already-completed CPU frame by the shared
64-bit frame ID. Query storage is fixed at 32 ranges/64 queries per frame context;
completed telemetry remains bounded at 512 frames. `--profile-gpu` explicitly
enables this path and implies CPU collection. The RHI exposes only backend-neutral
capabilities and completed ranges, never Vulkan query objects.

The contracted current ranges are implemented: full frame, opaque and selection
GBuffer, deferred lighting and selection outline, both legacy transparency
copy/depth/forward layers, and UI. The same scopes emit Vulkan Debug Utils labels
when GPU profiling is requested, enabling external tools to identify them.

Engine allocation accounting now occurs at the centralized
`vkAllocateMemory`/`vkFreeMemory` boundary. Each buffer/image carries category,
logical requested bytes, committed requirement bytes, memory type/heap, and
lifetime. Live/peak category and total values are bounded fixed-size data.
Environment textures are classified at allocation through a backend-neutral
texture usage, rather than temporarily inflating ordinary texture peaks.

`VK_EXT_memory_budget` is enabled when available. Driver heap usage/budget remains
separate from engine-committed totals. Swapchain images are reported as external
logical payload with committed bytes explicitly unavailable. Current per-image
targets remain labelled `persistent.legacy_per_image`; M0 does not call them
transient before M1's render graph exists.

JSON Lines frames now contain delayed GPU ranges, availability/overflow, allocation
deltas and totals, categorized live/peak memory, engine heap commitment, driver
heap budget/usage, and external-scope diagnostics. The profiler panel presents
delayed GPU statistics and current categorized memory without owning collection.

## Automated and validation evidence

Debug and Release builds pass all four CTest executables. CPU profiler tests cover
64-bit and wrapping timestamp conversion, delayed frame-ID attachment,
unavailable-sample exclusion, bounded ring behavior, memory allocation/free,
category reclassification, live/peak totals, and JSON serialization.

A Debug/validation run used eight warm-up frames and 64 measured frames after the
final Debug Utils integration. All 64 frames contained GPU and memory data; all 64
reported driver heap budget; GPU dropped/unavailable count was zero. The run
exited normally with no Vulkan validation message. An earlier 128-frame validation
run likewise retained shared frame IDs 9 through 136 across more than 60 query-pool
reuse cycles, including final-frame collection during cleanup, with zero drops.

## External-profiler cross-check

Nsight Systems 2026.1.1 was the installed external Vulkan profiler; Nsight
Graphics was not installed. A CLI capture used Vulkan annotations and independently
found all 12 Debug Utils range names with equal instance counts and expected nesting
and order.

Absolute marker timing from Nsight Systems individual-workload mode was not an
acceptable numerical oracle. It materially instrumented every Vulkan workload:
projected child medians totalled roughly 2.23 ms while the in-command-buffer
timestamp for the same captured work was 1.123392 ms, and its nested `gpu.frame`
projection frequently collapsed to 1 ns. Batch mode avoided individual-workload
cost but did not project submarkers, and queue-submit spans included semaphore/queue
latency excluded by `gpu.frame`. These results validate range discovery and expose
tool limitations; they are not represented as timing agreement. M0.5 retains the
final exact external timing cross-check for a tool/mode that can measure identical
boundaries without this distortion.

## 4K memory reconciliation

The current local car diagnostic at 4K reports 1,547.219 MiB engine-committed live
across 105 allocations and a 2,138.184 MiB observed peak during loading. Logical
requested live memory is 1,540.184 MiB. The difference is Vulkan requirement
alignment and must not be confused with driver heap usage.

The seven swapchain-sized engine target categories reconcile as follows:

- three FP16 GBuffer categories: 199,065,600 requested bytes each;
- opaque depth, legacy scene color, legacy copy, and glass depth:
  99,532,800 requested bytes each;
- total logical per-image targets: 995,328,000 bytes (949.219 MiB);
- committed per-image targets after Vulkan requirements: 1,002,700,800 bytes.

The three external 4K swapchain images contribute a separate 99,532,800-byte
(94.922 MiB) logical payload. Their committed allocation is unavailable and is not
added to engine totals. The sample environment is 512 MiB logical/committed; normal
textures are 59.267 MiB logical. Upload staging is zero live after initialization
but preserves a 590.965 MiB peak. All post-warm-up allocation deltas in the
1,000-frame run were zero.

The reference RTX 4090 exposed two heaps through `VK_EXT_memory_budget`. Engine
commitment summed across heaps exactly matched the allocator total. Driver
usage/budget was serialized separately and was never added to the 1,547.219 MiB
engine figure.

## Remaining limits

- Upload GPU duration remains unavailable because uploads use a separate blocking
  command context without safe timestamp ownership.
- Pipeline-statistics transparency invocations remain optional and disabled.
- Allocations outside the centralized Vulkan allocator, descriptor/pipeline driver
  storage, and C++ heap allocation are outside engine Vulkan totals.
- Requested image bytes are logical texel payload; committed bytes are Vulkan
  memory requirements. Neither is a substitute for driver residency.
- The local car/HDRI remain diagnostic assets under the M0.1 licensing/provenance
  constraints.

No ADR was added or superseded by M0.3.
