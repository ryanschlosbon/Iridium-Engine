- Status: Accepted on 2026-08-02

## Accepted behavior and architecture

Scene cooking now produces `iridium.scene.runtime` schema 1 inside the accepted M3
cooked-artifact envelope. The binary payload has a fixed little-endian scene header,
registry-manifest hash, deterministic section directory, `SCN1`, `STR1`, and `ENT1`
sections, plus one stable-ID component section per present registered runtime type.
Entities, dependencies, strings, types, and component instances use canonical
ordering; offsets and ranges are checked before use. The output is independent of
transient ECS handles, hash-container iteration, task order, source paths, and RTTI
names.

`RuntimeComponentRegistry` is the single explicit component contract. Frozen
descriptors now include cooked measure/write/read callbacks in addition to source
schema behavior, and the manifest hash covers stable ID, version, and runtime
requirements. Core Name, Transform, Relationship, Mesh, and Light adapters cook and
load through that contract. Unknown source components, missing cooked callbacks,
unsupported versions, duplicate instances, and manifest disagreement fail instead
of being silently reduced.

The source-free runtime loader validates the M3 envelope and content hash, artifact
identity, platform/profile/CookKey, scene and component versions, directory
ordering/alignment/ranges, entity identities and hierarchy, dependencies, component
streams, and stable references before constructing a staging world. Required asset
dependencies must be ready; optional dependencies may remain unresolved; pending
required dependencies produce a distinct retryable result. A failed validation,
dependency, decode, reference-fixup, or post-load step retains the prior active
world. Success commits by the same address-stable, allocation-free swap established
in M4.3.

`IridiumCookScene` is the non-window scene cook entry point. Its metadata must
explicitly select `iridium.scene@1`. A cold cook strictly parses current-schema JSON,
stages it, derives exact required/optional asset dependencies, verifies the supplied
dependency hashes, computes the scene compiler/CookKey identity, and publishes via
the M3 local DDC with an atomic receipt. A valid receipt and DDC artifact still
receive full cooked validation but skip JSON parsing and scene compilation.
Corrupt or missing DDC state is rebuildable from the source scene, metadata sidecar,
and declared dependency hashes.

Scene cooking deliberately uses a dedicated strict pipeline over the shared M3
artifact/DDC services rather than pretending the generic M3 `AssetImporter` can
carry a typed staging world or externally resolved scene dependency graph. The
metadata importer identity, compiler version, target, quality policy, dependency
requests, source hash, feature version, and registry manifest all participate in
the receipt/CookKey identity. The M3 envelope does not serialize quality policy as
a separate field, so the complete target remains protected by the CookKey and
receipt and is checked through the expected CookKey at runtime.

`IridiumInspectCookedScene` validates and reports scene GUID, target, hashes,
manifest, entity/component counts, types, sections, and dependency policy without
source JSON or authoring code. `IridiumCookedSceneBenchmark` supplies reproducible
1k/10k/100k Release scale evidence.

Automated coverage exercises exact schema sections, target and manifest validation,
source-to-cooked semantic equality for every core adapter, unknown-source rejection,
missing callbacks, corrupt outer/inner headers and hashes, section order/alignment/
ranges, unsupported versions, malformed strings/entities/component streams,

every staged-load failure class. The CLI integration test performs a cold cook, a
receipt/DDC hit with `sourceParse:false` and `sceneCompile:false`, and a source-free
inspection of the resulting artifact.

`SceneRuntimeBoundaryTests` links only `IridiumSceneRuntime` and
`IridiumCookedArtifact` plus platform libraries. Its sources and link graph contain
no editor, ImGui, native dialogs, SQLite, glTF, importer, authoring, or nlohmann JSON
dependency. This is the production-style runtime boundary required by M4.4.

## Performance and visual disposition

At 1k/10k/100k entities, artifacts use 56.720/56.072/56.007 bytes per entity.
Median CPU-ready staging is 1.112/12.193/148.105 ms; warm full-artifact DDC reads
are 0.706/6.009/62.028 ms. Commit is 0.0000/0.0002/0.0007 ms median and allocation-
free at every scale. The exact protocol and complete allocation/memory results are
in the performance report.

The 100k CPU-ready p95 is 254.994 ms and its staging path requests 96.29 MiB through
800,271 allocations. That is accepted as a visible one-shot load risk because the
active-scene commit is constant-time and no work runs in the steady frame loop; it
is not accepted as a future streaming target. Allocation reduction and scheduled
incremental staging remain follow-up opportunities after representative runtime
scene streaming requirements exist.

M4.4 changes no renderer, shader, material, RHI, render-graph, color, or GPU resource
contract. It therefore has no expected image difference and claims no GPU timing or
VRAM change. The last 4K visual/validation baseline remains M4.3.

## Remaining risks and next slice

- The cook executable is headless but still compiles the current core component
  adapter translation unit with ImGui support because runtime component types retain
  component-owned inspector hooks. This does not cross the runtime product boundary;
  M4.5 removes that authoring-tool linkage and moves all component UI to editor
  registries.
- Large scenes should eventually stage on jobs or through incremental cells rather
  than monopolize one thread. The current all-or-nothing loader intentionally
  prioritizes complete validation and rollback safety.
- Runtime application startup has not been switched from the editor document path;
  the runtime-only target and tools establish the production contract that a later
  game/application packaging path can call without adding source support.
- Remote/shared DDC and independently resident scene cells remain outside M4.4.

No ADR changed. This slice implements the cooked-runtime direction already accepted
by ADR-0004 and advances M4.5.
