# M5.1 Photometric Light v2 - 2026-08-08

Status: Accepted M5.1 contract and characterization.

## Result

Light source and cooked component version 2 makes color and photometric units
explicit without changing renderer output. Directional lights persist lux; point
and spot lights persist on-axis candela; color persists as nonnegative linear
Rec.709/D65; range, source radius, cone half-angles, shadow quality, and priority
have named units and deterministic defaults. The stable component identity remains
`iridium.component.light` and the cooked section remains `LGT1`.

Version-1 and legacy-v0 sources remain readable. Migration preserves numeric RGB,
intensity, range, radius, cones, and shadow intent, emits ordered structured
warnings, and only writes v2 on explicit save. Legacy Area remains readable with
`light.area_unsupported`, while strict cooking fails instead of substituting an
unapproved emitter.

## Protocol

- Release, MSVC 19.51.36252.0, reference CPU.
- Generated deterministic scene: 1,000 root entities, each with Relationship and
  one Directional/Point/Spot light in round-robin order.
- Two warmups and 15 measured samples for source read/migration and current-schema
  read; two warmups and 15 samples for current-schema stage plus cook.
- Timings exclude generated-source construction. Allocation counters cover global
  C++ `new`/`new[]` calls and requested bytes in the measured operation.
- Editor transaction rerun uses the accepted M4.6 protocol: 30 independent samples
  at 1, 100, and 10,000 targets.

## Source migration and cooking

| Workload, 1,000 lights | Median | p95 | Allocations | Requested bytes |
|---|---:|---:|---:|---:|
| Read v1 and migrate to v2 | 26.190 ms | 29.441 ms | 260,633 | 16,757,205 |
| Read current v2 | 21.357 ms | 22.604 ms | 214,610 | 11,682,289 |
| Stage and cook v2 | 8.556 ms | 9.081 ms | 72,451 | 5,366,915 |

Visible migration diagnostics cost 4.833 ms at the median versus already-current
v2 (+22.6%), 46,023 allocation calls (+21.4%), and 5,074,916 requested bytes
(+43.4%) for 1,000 lights. This is one-time editor/cook-host work; source-free
runtime loading never performs it. The benchmark's 1,000-light cooked artifact is
122,208 bytes.

The compact generated v2 source is 468,970 bytes versus 357,970 bytes for v1
(+31.0%) because unit-explicit field names and both stable intensity fields are
persisted. Explicit canonical save is 871,991 bytes with the existing two-space
source formatting.

The frozen M4 fixture artifact moves from 1,568 to 1,576 bytes (+8, +0.51%). The
three-light M5 fixture moves from 1,776 to 1,808 bytes (+32, +1.80%). Historical
hashes remain in their contracts; named `m5_1Supersession` blocks freeze the new
manifest, canonical, CookKey, artifact hash, and byte count.

## Editor transaction comparison

The 10,000-target transaction rerun is 0.1072 ms median / 0.1204 ms p95 / 0.1214 ms
p99 for apply, 0.0491 / 0.0526 / 0.0592 ms for undo, and 0.0446 / 0.0475 /
0.0483 ms for redo. Apply retains the accepted one 120-byte allocation independent
of target count; undo and redo remain allocation-free. Estimated history remains
2,470,140 bytes, or 247.014 bytes/target. This matches or improves the accepted
M4.6 service baseline; Light-specific tests additionally cover v1 open without
dirtying or rewriting, type change, inactive-unit preservation, undo, redo, and
explicit v2 save with unknown-property preservation.

## Visual, GPU, and memory impact

No renderer reads `LightComponent` yet; GPU passes, shaders, captures, timestamps,
and VRAM are unchanged by M5.1. The accepted M5.0 five-fixture 4K captures and
byte-identical M4 sample-car final SDR therefore remain the visual baseline. M5.2
must add extraction without shading; M5.4 is the first slice authorized to change
direct-light output.

The M5.0 retained-allocation discrepancy of one 8-byte call remains open and is not
attributed to Light v2. M5.1 adds no steady-frame renderer allocation path.
