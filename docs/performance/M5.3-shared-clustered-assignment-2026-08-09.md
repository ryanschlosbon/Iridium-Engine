# M5.3 Shared Clustered Assignment — 2026-08-09

## Result

M5.3 is accepted. Iridium now builds one graph-declared clustered-light product for
deferred/material-resolve and complex-forward consumers. The selected production
grid is 32x32 screen tiles with 24 logarithmic view-depth slices. Directional lights
occupy a bounded global list; point and spot lights occupy compact per-cluster lists
sorted by transient light slot. The product is valid for zero lights, remains bounded
at every write, and switches as a whole to an ordered top-64 list on any capacity
overflow.

This slice deliberately does not change final direct-light evaluation. M5.4 consumes
the shared product and removes the fixed demonstration lights.

## Architecture and behavior

- `ClusterGridConfig` and `ClusterFrameParameters` are backend-neutral. Active-camera
  near/far planes define Vulkan 0..1 logarithmic depth slices; there are no shader
  near/far constants.
- The production graph owns clear, count, hierarchical scan, fill, deterministic
  sort/finalize, and fence-delayed diagnostic readback. Storage read/write hazards
  and buffer transitions are explicit in the graph executor.
- Count/fill are light-centric but use one workgroup per light, with lanes striding
  the conservative cluster volume. This replaced the rejected one-thread-per-light
  implementation that measured 6.2–32.1 ms in normal 4K fixtures.
- Nonempty lists are compacted during fill. Lists of at most 32 entries are packed
  across native subgroups and sorted with a bitonic shuffle network; the uncommon
  dense lists use a bounded shared-memory network. Normal membership and order are
  deterministic despite atomic fill scheduling.
- Limits are 256 local lights per cluster, 4,194,304 local references, eight global
  directional lights, and 64 fallback lights. Overflow publishes no partial local
  product. CPU-prepared fallback order is priority, shadow intent, conservative
  camera contribution, then stable scene UUID; the CPU reference and Vulkan upload
  use the same selection function.
- Deferred and forward scene descriptor layouts bind the same records, global list,
  cluster headers/indices, fallback list, diagnostics, and cluster parameters. No
  forward-only scheduler or assignment exists.
- Runtime counters cover cluster count, exact buffer bytes, requested/published
  references, used clusters, maximum occupancy, fallback/dropped lights, and overflow
  code. CPU ranges isolate fallback selection and command recording; GPU timing
  isolates the entire cluster build.
- `cluster-occupancy` and `cluster-overflow` debug views are exposed through CLI and
  editor menus. Overflow is an unmistakable magenta diagnostic.

## 4K configuration decision

Release measurements used the RTX 4090 / driver 610.74, 3840x2160, two warmups, and
eight measured frames. Values are GPU cluster-build median / p95.

| Grid | Lights | References | Used clusters | Maximum | Median | p95 |
|---|---:|---:|---:|---:|---:|---:|
| 16x16x24 | 64 | 87,993 | 24,664 | 12 | 0.118 ms | 0.122 ms |
| 16x16x24 | 512 | 1,749,648 | 149,420 | 34 | 0.787 ms | 0.812 ms |
| 16x16x32 | 512 | 2,054,072 | 183,365 | 27 | 0.997 ms | 1.039 ms |
| **32x32x24** | **64** | **23,903** | **6,595** | **12** | **0.055 ms** | **0.057 ms** |
| **32x32x24** | **512** | **454,085** | **38,025** | **34** | **0.267 ms** | **0.273 ms** |
| 32x32x32 | 512 | 532,970 | 46,755 | 28 | 0.300 ms | 0.322 ms |

The selected 32x32x24 candidate is 53.5% faster at 64 lights and 66.0% faster at
512 lights than 16x16x24. Its conservative consumer-loop proxy rises 8.7% at 64
lights and 3.8% at 512 lights, which is a favorable exchange for the measured build
and memory reduction. Adding eight depth slices is slower and produces more
references, so 24 slices remain production policy.

The selected product requests 19,914,116 bytes (18.991 MiB) per frame context,
37.982 MiB across the current two contexts. This is 8.886 MiB per context / 31.9%
less than 16x16x24. Relative to the M5.2 graph, requested graph memory grows exactly
39,828,232 bytes and committed memory grows 39,828,256 bytes. Persistent cluster
inputs/readback add 5,120 bytes at the common 512-light capacity and 33,792 bytes at
4,096 lights.

A final selected-default rerun measured 0.241 / 0.259 ms for 512 lights. The empty
product costs 0.0189 / 0.0203 ms. The deliberately excessive 4,096-light fixture
hits per-cluster capacity, publishes the ordered 64-light fallback, explicitly drops
4,032 lights, and costs 1.911 / 1.921 ms. CPU fallback selection is 0.028 / 0.029 ms
at 512 lights and 0.087 / 0.136 ms at 4,096 lights; total lighting record work at
512 lights is 0.068 / 0.078 ms CPU.

## Risks and deferred work

- The fast sort uses a 1,024-invocation workgroup and subgroup operations available
  on the reference class of Vulkan 1.3 hardware. Device capability policy and a
  smaller-workgroup variant should be added before broad non-reference hardware is
  claimed; this is not a correctness risk on the accepted target.
- The 4,096-light fixture is intentionally outside the gameplay budget. Its visible,
  deterministic fallback is accepted behavior, not a promise to shade 4,096 dense
  overlapping local lights below 1.4 ms.
- M5.3 binds but does not yet consume cluster lists in direct lighting. M5.4 must
  prove deferred/complex-forward parity, consumer-loop cost, and identical fallback
  behavior in both consumers.
- No ADR changes. M5.3 implements the accepted ADR-0006/ADR-0007 direction.
