# M7.6 view-owned depth-history publication — 2026-09-10

## Result

The opt-in live depth-pyramid path now publishes into two independent persistent
histories: scene view 0 and asset-preview view 1. The render scheduler's rotating
frame-context index is no longer treated as temporal-view identity. Each history
publication carries the actual `DepthPyramidHistoryOwner`: view identity, scene
epoch, aggregate depth-content revision, projection revision and reset revision,
plus the global Vulkan submission serial and the allocated image generation.

The scene owner uses `SceneWorld`/GPU-scene epoch. Asset-preview ownership uses the
preview document's unique session identity, so closing/reopening a viewer cannot
inherit an older preview. The depth-content revision hashes the actual opaque and
depth-writing complex-forward packet streams, including geometry, transform,
pipeline, material handle and packed material revision. This deliberately
invalidates more often than a selective occluder journal, but cannot preserve a
history across a known submitted-depth change. Projection revision hashes the
actual projection matrix; framing/camera cuts remain explicit reset revisions.

The fixed-capacity backend-neutral `DepthPyramidHistoryPublicationTracker` records
the producing frame slot but publishes metadata only after that slot's fence has
completed. If a newer submission for the same view is already scheduled, completion
of an older slot cannot replace it. All publications are cleared when resize,
transport or graph reallocation advances the image generation. `waitForAllFrames`
now also advances the scheduler's completed global serial, closing a pre-existing
completion-accounting gap exposed by explicit end-of-run history collection.

## Vulkan storage and validation

The graph still builds one transient chain per frame context. A transfer pass then
copies every mip into the selected persistent view image and returns that image to
sampled state. This is a deliberately measurable integration bridge: it establishes
correct independent lifetime before the future culling consumer exists, but it is
not the final allocation topology.

The one-shot live oracle now reads both the graph-built chain and the copied
view-history chain. At 1280x720, Debug empty-scene and Release populated
`m7_three_dense_all_visible_v1` runs each inspect 1,228,763 texels over 11 mips.
Both report zero invalid source depths, zero build mismatches, zero history-copy
mismatches and zero Vulkan synchronization errors.

A 100-frame native-4K Release run on the RTX 4090, with validation and profiling,
measures the combined build plus publication copy at 0.162816 ms median and
0.188416 ms p95. Relative to the prior build-only allocation, the two view-owned
chains add exactly 88,472,440 requested bytes, 91,594,752 committed bytes
(87.3515625 MiB), and two allocations. The resulting experimental topology owns
four chains total: two frame-context build chains and two view histories. These
figures are qualification costs, not production admission evidence; the next
topology should build directly into safe view-owned generations or otherwise remove
the duplicate chains and full-chain copy before admission.

Evidence: `out/benchmarks/m7.6/view-history-2026-09-10/`. The corrected timed run is
`candidate-timed.jsonl`; `candidate.jsonl` predates widening the GPU timer to include
the publication copy and is retained only as diagnostic evidence.

## Verification and remaining work

- Debug and Release engine builds succeed; portable CTest passes 77/77 in both.
- Render-graph tests require build -> ready -> publish -> optional validation ->
  sorted-transparency order and transfer-source capability.
- Backend-neutral tests cover independent views, early completion, suppression of
  an older completed image when a newer one is scheduled, and generation reset.
- A populated 30-frame Release run switches scRGB -> HDR10 -> SDR with validation
  enabled and no Vulkan errors, exercising destruction/reallocation and generation
  invalidation across three live output rebuilds.
- The experimental path remains default-off and performs no occlusion rejection.

Next, bind a bounded GPU query/compaction stage to only an eligible completed
history, compare its decisions with the CPU oracle, and record fail-visible reasons.
Alternating/throttled editor views, motion, disocclusion, new residency, resize and
transport changes still require live temporal qualification before any rejection
can become a production option. No ADR changed.
