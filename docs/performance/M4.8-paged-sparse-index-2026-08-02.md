# M4.8 Paged Sparse ECS Index Evidence - 2026-08-02

## Result

M4.8 accepts a paged 32-bit sparse component index while retaining the existing
dense component/entity arrays, generational handles, and view API. The change is
narrower than an archetype migration and does not affect scene schemas, stable
UUID identity, editor contracts, or dense iteration order.

The candidate passes the milestone's 15% improvement / 5% dense-regression policy.
At 100,000 entities, random hit and miss p95 improve by 72.6% and 98.6%; the two
representative component views improve by 57.6% and 75.0%; hierarchy traversal
improves by 90.8-91.8%; and dense Transform iteration changes by -1.0% (an
improvement). One-million-entity Transform-only and mixed creation improve by
61.5% and 66.1%, while requested temporary allocation falls by 58.7 MiB and
203.4 MiB respectively.

## Storage decision

Each component pool still owns contiguous `components` and `entities` vectors.
Its former `unordered_map<uint32_t, size_t>` lookup is replaced by a demand-
allocated sparse directory with 1,024 32-bit slots per page. Missing pages imply
absence; populated entries hold a dense-array index; the full dense entity handle
remains the generation authority. Empty pages are released after removals. Adding
a component rolls back both dense vectors if sparse-page allocation fails.

This shape follows the sparse-set family used by performance-oriented ECS designs:
it preserves cache-friendly dense iteration and O(1) lookup without paying a hash,
node, or per-entry allocator cost. Pages avoid reserving a flat sparse array up to
the highest entity index. Archetypes and cached query ownership remain deliberately
deferred because the measured view intersections no longer justify that complexity.

## Method

- Configuration: MSVC Release on the M4 reference workstation.
- Seed: fixed benchmark seed `0x4d345343454e45`.
- Samples: one warmup and 30 measured samples per case.
- Comparator: identical executable matrix, fixture sizes, operation counts, and
  global `new`/`new[]` requested-byte instrumentation before and after the change.
- Baseline: `data/M4.8-ecs-before-2026-08-02.json`.
- Candidate: `data/M4.8-ecs-paged-candidate-2026-08-02.json`.
- Identity noise audit: five independent 30-sample identity-only runs in
  `data/M4.8-ecs-identity-rerun-1.json` through
  `data/M4.8-ecs-identity-rerun-5.json`.

## Allocation and correctness evidence

| Creation case | Before requested | Paged requested | Reduction |
|---|---:|---:|---:|
| Transform-only, 1,000,000 | 603.7 MiB | 545.0 MiB | 58.7 MiB |
| Mixed components, 1,000,000 | 1,407.2 MiB | 1,203.8 MiB | 203.4 MiB |

Focused tests prove that indices 0 and 1,000,000 allocate only two sparse pages,
that removing their last entries releases both pages, and that one optional
component on entity 99,999 allocates one page. A deterministic 100,000-operation
property test compares create/add/update/remove/destroy/reuse against independent
reference maps and sets. It also checks stale handles, typed and erased lookup,
dense-order independence, and multi-component view intersection.

The complete Debug and Release builds pass 59/59 CTests. The new
`RegistryPropertyTests` is included in both suites.

## Identity variance audit

The first full candidate matrix showed two apparent identity-only p95 regressions:
10k create/bind at +7.8% and reverse lookup at +14.0%. Neither path reads a
component pool. Five isolated reruns produced a median p95 of 1.882 ms for 10k
create/bind versus the 2.623 ms baseline (-28.2%), and 39.367 ms for reverse
lookup versus 42.490 ms (-7.4%). Allocation counts and requested bytes are
identical. The full-matrix readings are therefore recorded as run variance, not a
causal storage regression.

## M3 renderer preservation

Five independent Release runs repeated the accepted self-contained sample-car
fixture at 3840x2160 with 500 warmup and 10,000 measured frames. Each run completed
with zero drops at the requested extent. Across the five-run medians:

| Metric | M3 accepted | M4.8 candidate |
|---|---:|---:|
| CPU frame median | 1.7080 ms | 1.2682 ms |
| CPU frame p95 / p99 | 15.4599 / 16.2975 ms | 16.0444 / 16.3950 ms |
| asset runtime tick p99 | 0.0029 ms | 0.0027 ms |
| GPU frame median | 0.8450 ms | 0.9481 ms |
| GPU frame p95 / p99 | 2.2391 / 3.3213 ms | 1.4860 / 1.6836 ms |
| requested live / peak | 897.558 / 972.257 MiB | 897.558 / 972.257 MiB |
| committed live / peak | 967.567 / 1,042.265 MiB | 967.567 / 1,042.265 MiB |
| C++ allocation calls/bytes median and p99 | 0 / 0 | 0 / 0 |

The CPU-only storage change cannot alter GPU commands; GPU medians vary by
0.103 ms while tails improve and remain far below the 10 ms base-frame contract.
VRAM is byte-identical to M3. Raw profiles are
`out/m4.8-car-benchmark-run-1.jsonl` through
`out/m4.8-car-benchmark-run-5.jsonl`.

A final 300-frame 4K Release run enabled Vulkan validation and completed with zero
validation warnings/errors, zero frame drops, and zero profiler overflow. It
measured 1.735 ms CPU median and 0.906 ms GPU median; steady C++ allocation median
and p99 remained zero. Raw profile: `out/m4.8-final-validation.jsonl`.

No visual path, shader, material, render graph, or GPU resource changed, so no new
visual comparator is required. The accepted M3 sample-car presentation and M4.7
viewport captures remain the visual baselines.

## Decision and fallback

The paged sparse index is accepted. The fallback remains the prior dense-plus-
unordered-map pool, preserved by the baseline data and small implementation diff.
No fallback was needed. No ADR changed; this is an internal ECS storage choice
within the accepted generational-handle and stable-scene-identity architecture.
