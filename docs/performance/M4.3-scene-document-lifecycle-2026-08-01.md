## Protocol

- Release, MSVC 19.51.36252.0, 32 logical processors.
- Each scale runs in a fresh process with one warmup and five measured samples.
- Fixed schema-1 scenes contain Name and Relationship components. Source sizes are
  0.42 MiB at 1k, 4.29 MiB at 10k, and 41.94 MiB at 100k.
- `parse` performs strict JSON parsing plus complete schema/component/reference
  validation. `stage` builds a complete rollback-safe `SceneWorld`. `capture`
  reconstructs the source document from the live world while retaining opaque data.
- `commit` measures only the address-stable active/staged world swap. Both worlds
  remain alive until timing and allocation collection end, so old-world destruction
  is not charged to the swap.
- `atomic save` writes a unique same-directory temporary, flushes it, reopens it,
  verifies SHA-256 and full source-scene semantics, then performs the platform atomic
  replacement with `.bak` retention.
- Allocation bytes are aggregate global C++ `new`/`new[]` traffic. Live private
  deltas are process samples while each result is alive, not object-size claims.

## Source-path scale and parser decision

| Workload | Entities | Median | p95 | Median allocations | Requested traffic |

| Strict parse/validate | 10,000 | 166.683 ms | 181.383 ms | 983,131 | 45.10 MiB |
| v0-to-v1 migration | 10,000 | 153.238 ms | 164.295 ms | 900,136 | 38.78 MiB |
| Strict parse/validate | 100,000 | 18,627.488 ms | 18,745.101 ms | 9,803,152 | 450.76 MiB |
| v0-to-v1 migration | 100,000 | 18,281.562 ms | 18,427.988 ms | 9,000,163 | 390.24 MiB |

Strict duplicate-key detection now keeps up to twelve keys inline and allocates a
hash set only for wider objects. A regression test crosses that threshold and proves
duplicate rejection remains exact. Against the accepted M4.2 100k result, allocation
calls fall from 11.90 million to 9.80 million (17.6%) and requested traffic falls
from 578.16 MiB to 450.76 MiB (22.0%). The current 100k p95 is nevertheless 2.18x
the M4.2 run, so this is an allocation improvement, not a latency acceptance claim.
Large authored JSON remains a measured editor-path risk.

The M4.4 cooked binary scene is the production-scale answer. M4.3 does not weaken
duplicate detection, semantic verification, atomic replacement, or rollback safety
to make source JSON appear cheaper. Streaming source parsing remains a later option
only if representative authored scenes justify the complexity.

## Verification and remaining acceptance work

- Full Debug build and CTest: 52/52 passed.
- Full Release build and CTest: 52/52 passed.
- Runtime scene boundary scan: no ImGui, native dialog, SQLite, source JSON,
  editor-document, or legacy serializer dependency.
- Production call-site scan: no `SceneSerializer` use outside its retained
  characterization implementation.
- Debug hidden-window material-lab smoke at 3840x2160: eight warmup frames and one
  measured frame with `VK_LAYER_KHRONOS_validation` enabled completed without a
  VUID or validation message. The run loaded the accepted self-contained cooked
  artifact, reported `source_import_ns = 0`, 0.408 ms GPU frame, 4.246 ms CPU frame,
  0.0876 ms editor initialization, and 0.0993 ms editor build. These single-sample
  Debug figures are integration evidence, not a performance baseline comparison.
  Raw profile: `out/m4.3-validation-4k.jsonl`.
- Release 3840x2160 material-lab editor profile: 500 warmup and 1,000 measured
  frames with validation enabled, zero dropped frames, and no validation message.
  Editor build is 0.0699 ms median / 0.2070 ms p95 / 0.3241 ms p99; total CPU frame
  is 2.9023 ms median, GPU frame is 0.3883 ms median, and steady C++ allocation
  median is zero. Raw profile: `out/m4.3-release-editor-4k-1000.jsonl`.
- Five independent Release launches measure editor initialization at 0.0211 ms
  median, down 60.7% from M3's 0.0537 ms. The unchanged 30-sample 100k inspector
  construction workload is 84.992 ns/op median with zero allocations versus
  89.908 ns/op in M4.1 and 130.111 ns/op in M4.0. Machine-readable evidence:
  `docs/performance/data/M4.3-ecs-editor-lifecycle-2026-08-01.json`.
- `git diff --check`: no whitespace errors; only existing Windows line-ending
  conversion warnings.
- Automated coverage includes failed-open retention, every atomic-save failure
  phase, sidecar rollback, backup and explicit orphan-temp recovery, stable UUID
  selection recovery, unknown payload retention, hierarchy/reference validation,
  GUID-only model/material authoring, and pending/failed/later-resident asset state
  without dirty-state changes.

M4.3 is accepted. The visible menu calls a dedicated document-command layer whose
Open/Save path/backup/temp recovery, failed-operation retention, and persistent-UUID
selection behavior are exercised directly by the document-service tests. This is
stronger and repeatable evidence than a manual click-through while leaving ImGui as
presentation only. No renderer path or GPU resource contract changed in this slice,
so no visual or VRAM delta is claimed by these CPU/document measurements.
