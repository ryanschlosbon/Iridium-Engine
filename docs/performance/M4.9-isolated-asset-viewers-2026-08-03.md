# M4.9 Isolated Asset Viewer Evidence - 2026-08-03

## Result

M4.9 is accepted. Models and materials open from the Asset Browser into stable,
deduplicated editor document tabs. One shared scene target presents the active
asset, matching the single-expensive-preview approach used by established
content editors: tabs preserve user context while only the active document pays
3D extraction and rendering cost.

Asset documents are keyed by `AssetGuid` and selected through an explicit frozen
asset-type/viewer registry. Model documents present themselves; material
documents retain their own material GUID while presenting and pinning the stable
owner-model GUID. Closing the final document for a presentation root releases its
runtime pin. No viewer operation creates, selects, or mutates a scene entity or
enters the scene transaction history.

## User workflow and presentation

- Double-clicking a model or material, or choosing **Open in Asset Viewer**, opens
  or activates its tab. Unsupported asset kinds retain Browser details/thumbnails.
- Left-drag orbits, middle-drag pans, the wheel dollies, and **Frame** restores the
  exact aggregate cooked bounds. Pitch, distance, and clip planes are bounded.
- Model presentation retains the model's per-primitive materials. Material
  presentation applies the selected stable material binding over the owner model.
- Standard, wireframe, glass-depth, and material/debug views reuse the production
  render target and debug-view boundary. The panel reports runtime preparation,
  last-known-good, failure, and diagnostic state.
- The active viewer supplies DPI-aware requested pixel extent and aspect fitting.
  Its orbit camera projection uses the committed render extent; the scene fly
  camera and scene selection are disabled while an asset document is active.
- `--open-asset-viewer GUID` provides deterministic automation. Interactive opens
  remain asynchronous; bounded command-line capture waits up to 30 seconds for
  the requested cooked revision so measured frames cannot capture a loading state.

## Correctness and lifecycle evidence

`EditorAssetDocumentServiceTests` covers explicit/frozen registration, model and
material open/close/reopen/activation, shared presentation-root pin reference
counts, runtime failure-to-ready updates, unsupported/parentless rejection, scene
entity/document-state/dirty/history isolation, wide and tall bounds framing, and
bounded orbit/pan/dolly controls. Existing viewport tests cover DPI pixel extent,
wide/tall aspect fit, minimized windows, debounce, clamp, and retry behavior;
asset runtime tests retain failure, last-known-good, pin, eviction, and retirement
coverage.

Debug and Release builds pass all 60 CTests. Normal application cleanup closes all
documents before the runtime service is destroyed, releasing the final pin. Three
Debug and two Release bounded runs exited normally under Vulkan validation with
zero reported warnings/errors, zero dropped frames, and zero profiler overflow.

## Decision and fallback

The reusable isolated viewer is accepted as editor-only architecture. It reuses
the existing production scene target instead of allocating a render graph per tab,
and stable document/presentation identities leave future texture, animation, or
shader viewers extensible without RTTI or path identity. Browser thumbnails and
details remain the fallback for unsupported types or unavailable 3D preparation.
No ADR changed: this implements the editor-only asset/viewer direction already
accepted by ADR-0004 and does not alter scene, cooked, material, or RHI schemas.
