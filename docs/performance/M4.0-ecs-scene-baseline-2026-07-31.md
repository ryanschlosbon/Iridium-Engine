## Environment and protocol

- Release, MSVC 19.51.36252.0, source commit
  `30252593f8fdd2de5dffbb8da31bb570ff49a7c0`; the intentionally dirty accepted
  M0-M3 worktree is recorded in the JSON.
- Core i9-14900K-class CPU, 32 logical processors, 68,466,892,800 physical bytes.
- Fixed seed `5570198094586900512`; one warmup and 30 measured samples per case.
- Every case reports min/median/p95/p99/max duration, nanoseconds per operation,
  global C++ allocation calls/requested bytes, working/private process deltas, and
  requested bytes per entity.
- Current Registry contract: dense component vectors plus per-pool
  `std::unordered_map<Entity, size_t>` and RTTI-keyed pool lookup.
- Current source scene contract: unversioned M3 GUID scene, treated by M4 as logical
  version 0.
- Stale-handle probes, persistent UUID maps, and cooked scene save/load are marked
  unsupported rather than fabricated. M4.1 and M4.4 append those cases.

Allocation figures cover C++ global `new`/`new[]` calls and requested bytes. Process
memory is sampled around the measured operation and does not claim driver or
filesystem-cache attribution.

## Decision

Retain dense component arrays. Dense iteration and dirty-update paths are strong,
and no measured alternative meets the plan's 15% p95 improvement gate. M4 is not an
archetype rewrite.

Random sparse hits, hierarchy depth/locality, view construction, hierarchy sorting,
and Inspector discovery degrade enough to remain targeted candidates. M4.1 first
adds correctness-required generational handles and UUID maps without changing pool
storage. M4.8 may test a paged sparse set or cached explicit views against this
baseline.

The dominant source-scene issue is the central JSON object graph. M4.2/M4.3 should
retain deterministic readable JSON while reducing redundant transient construction
where practical. M4.4's cooked binary is the production runtime scaling path.
