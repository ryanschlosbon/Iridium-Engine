# M7.8 live scene-depth page demand

Date: 2026-09-30
Status: integrated receiver-demand qualification; M7.8 remains active

## Behavior and ownership

The default-off `--experimental-virtual-shadow-resources` path now records
`shadow.virtual.depth-mark` after `forward-opaque`. Thus its sampled D32 depth
contains conventional deferred and complex-forward opaque surfaces. Every depth
pixel contributes to its finest containing directional clip page; there is no
spatial subsampling. The existing full-view accumulator initializes every page
cell, then the hierarchical compactor emits bounded deterministic requests.
Missing/unknown-bound packets run zero-mark compaction to overwrite stale counts.
Clip stacks that exceed workspace capacity or signed GPU addressing are rejected
before upload, with `shadow.virtual.clip.grid_rejected` and conventional fallback.

The graph orders command-embedded clip uploads, depth sampling, storage writes and
`shadow.virtual.request-readback`. Borrowed per-slot working buffers retain their
access tracking across reuse. The readback pass also declares a depth transfer
read for explicit qualification. A nearest sampler and immutable slot descriptors
are reused; depth image rebinding occurs only after that slot retires, including
topology/extent changes. No additional page-cell or per-pixel GPU receiver storage
is allocated for the live path.

Each slot owns a coherent telemetry/request readback, consumed after its fence and
before its CPU clip snapshot is overwritten. Collection checks ABI/level errors,
capacity/overflow arithmetic, nonzero coverage, page windows and exact clip
metadata. Cleanup waits for both slots and collects final pending results.
Request readbacks are qualification storage, not a production CPU-driven shadow
allocator. The current live path still publishes only the first directional light.
Both caster layers use the complete conservative caster revision.

`--virtual-shadow-depth-qualification-oracle` enables the above experiment plus an
expensive, separate full-depth readback and CPU reference. Each retired slot keeps
its own extent and inverse view-projection. The CPU reconstructs every pixel and
compares request addresses/order, coverage, priorities, layers and overflow
telemetry exactly. A mismatch fails the run; it is never silently tolerated.
Readbacks resize after slot retirement and are destroyed at cleanup. This option
is not enabled by ordinary Vulkan validation and must not be used for performance
admission. At 4K it adds 33,177,600 readback bytes per slot (66,355,200 total), plus
large temporary CPU receiver arrays; normal demand-only runs allocate none of those
depth buffers. Transparent-only receiver coverage remains an unimplemented gate.

Interfaces/files: `VulkanVertexBackend.h/.cpp` dispatch, slot readbacks and exact
oracle; `VulkanVirtualShadowResources.h/.cpp` persistent nearest sampler and
request readback ownership; `VulkanProductionRenderGraph.cpp` depth/compute/transfer
dependencies; application/backend configuration and CLI tests; executor topology
tests; `assets/m7-virtual-shadow-depth-qualification-manifest.v1.json`; latest M5
contract fingerprints. No virtual page is rasterized or sampled yet.

## Correctness evidence

RTX 4090 / i9-14900K, Windows, MSVC Debug and Release:

- Full builds succeed and all 78 CTest tests pass in both configurations. Executor
  tests additionally require marking after opaque forward, storage read/write
  access, sampled depth and subsequent transfer reads. CLI tests require the
  oracle to be opt-in and to enable its prerequisite resources.
- Standalone Vulkan marking tests pass in both configurations with synchronization
  validation: camera clip scroll, forward/reverse and invalid depth, perspective
  and singular reconstruction, odd extents, full 8,294,400-pixel input, populated/
  empty two-slot reuse and deterministic bounded capacity/overflow all match.
- A twelve-frame 1280x720 Debug launch produces 17 requests in both slots, with
  zero overflow and an empty validation error log. The independent six-frame
  depth-oracle launch matches all 17 addresses and 121,104 receiver samples.
- Native-4K Release with validation and the moving M7.7 contact fixture runs twelve
  measured frames. Retired slots match exactly as demand changes from 210 to 60
  pages and 1,165,320 to 674,040 covered pixels. Both final slots are also checked
  during cleanup. Artifacts: `out/m7_8_native4k_motion_oracle_20260930.*`.
- Native-4K Debug empty-light fixture produces zero clips/requests across both
  slots without stale output. The complex-closure fixture requests five opaque
  forward draws; the CPU/GPU comparison matches 90 pages and 836,434 covered pixels.
  Artifacts: `out/m7_8_depth_empty_20260930.*` and
  `out/m7_8_depth_complex_20260930.*`. The fixture camera observes the authored
  front-facing triangles; the earlier opposite-side attempt had no coverage and
  was not counted as complex-material evidence.
- Debug combined depth-pyramid resize validation and full-depth oracle passes
  1280x720 -> 960x540 -> 1600x900 -> 1280x720, with three successful graph rebuilds

  not minimize/zero-extent behavior. Artifacts: `out/m7_8_depth_resize_20260930.*`.
- Matched native-4K final captures at measured frame 6 are byte-identical with and
  without the demand-only experiment: SHA256
  `b03cc977ab54e11cde78d820a3de6b34192dbbcf13b0c5d8b11fcd0c0c383701`.
  Artifacts: `out/m7_8_depth_baseline_capture_20260930/` and candidate counterpart.
  No shadow-quality improvement is claimed; conventional lighting remains active.

The complete GPU median and p99 regress because this adds receiver-demand work
while still retaining all conventional shadows. These numbers establish cost,
not a production VSM win or admission. Profile the coverage-sensitive tail before
admission; do not hide it behind the favorable median. The GPU demand range excludes
request readback; complete-frame timings include it. CPU frame scopes include
submission/presentation/waits and are not pure CPU publication cost. This fixture
is deliberately small, not a dense-scene scalability claim. The capacity rejection
guard added after these runs does not change GPU work, but its CPU cost still
requires a subsequent matched measurement if retained in a production candidate.

The persistent pool/table/working sets remain 93,064,256 bytes (88.753 MiB).
Request readbacks add 262,208 bytes; enabled-minus-disabled requested live bytes
are exactly 93,326,464 in every paired run. Baseline requested live allocation is
2,044,501,328 bytes versus 2,137,827,792 enabled. Full-depth qualification buffers
are not included in that delta. Default-off virtual storage remains zero.
