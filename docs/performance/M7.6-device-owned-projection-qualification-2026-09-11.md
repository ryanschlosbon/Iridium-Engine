# M7.6 device-owned projection qualification — 2026-09-11

## Result

The default-off `--experimental-depth-occlusion-query` route now runs a second
qualification oracle that constructs conservative occlusion queries directly from
the live GPU-scene transform, instance, primitive, geometry, and indirect-candidate
tables. It uses the global view constants and the exactly-adjacent, same-view depth
history already admitted by the M7.6 ownership contract. It remains diagnostic:
neither oracle changes an indirect command or removes a draw.

The original CPU-projected/device-tested stream remains the safety reference. Each
frame context now retains the CPU-query-to-candidate mapping, CPU-frustum verdict,
candidate primitive identity, and an independent device-owned result stream until
its fence completes. The device-owned result is rejected as invalid unless its ABI,
primitive identity, tested/fail-visible state, mip, one-to-four sample footprint,
depth, boolean verdict, and projection-rejection code are all valid. A device-owned
occlusion verdict for CPU-visible work is an immediate qualification failure unless
the independently projected CPU query also reports occluded.

The projection deliberately matches the CPU oracle's transformed world-space AABB,
not the tighter oriented box. It then expands the rectangle by two pixels rather
than one and moves nearest depth another `0.000002` toward the camera. Consequently
float precision differences can only make the device-owned route retain more work.
Malformed references, invalid bounds or projection, depth-plane intersections,
outside-view candidates, small bounds, and extent disagreement all write explicit
fail-visible results.

New delayed counters are:

- `depth.occlusion.gpu_scene.requested`
- `depth.occlusion.gpu_scene.tested`
- `depth.occlusion.gpu_scene.would_reject`
- `depth.occlusion.gpu_scene.fail_visible`
- `depth.occlusion.gpu_scene.invalid_results`
- `depth.occlusion.gpu_scene.unsafe_mismatch`

The work is timed as `gpu.depth.occlusion-gpu-scene-query`. The existing CPU-built
query stream and its counters remain unchanged so the two routes can be compared on
the same history and frame.

## Correctness and lifecycle evidence

All live runs used the Release build on the RTX 4090 with Khronos validation,
synchronization validation, and process-local suppression of unrelated implicit
overlay layers.

The frozen 32-frame `m7_occlusion_depth_stack_v1` temporal run passes with zero
invalid device-owned results and zero unsafe mismatches:

- frame 1 has no history and performs no query work;
- frames 2-12: 404 requested, 379 tested, 25 fail visible, 73 device-owned
  `would_reject` versus 88 from the CPU-projected oracle;
- frame 13 is the deterministic camera cut, rejects history as `CameraCut`, and
  performs no query work;
- frames 14-32: 404 requested, 395 tested, 9 fail visible, 42 device-owned
  `would_reject` versus 48 from the CPU-projected oracle.

The lower device-owned rejection totals are intentional evidence that its extra
pixel/depth margins are conservative.

The 16-frame `m7_three_dense_one_visible_v1` off-frustum run dispatches all 303
candidates. Per eligible frame, 111 are tested, 192 explicitly fail visible, and
both query routes report 16 would-reject verdicts. Invalid results and unsafe
mismatches remain zero. This proves that an unqueried CPU-frustum-rejected candidate
is not confused with an unsafe retained candidate.

A 30-frame scRGB -> HDR10 -> SDR rebuild run has four history-unavailable frames,
then 26 consecutive eligible frames with 303 requested, 288 tested, 15 fail visible,
28 device-owned would-reject verdicts, and zero invalid results or unsafe mismatches.
Descriptor recreation, history generation reset, and recovery are clean.

Debug and Release builds succeed, and both portable test suites pass 77/77. The new
compute shader compiles in both configurations. Production occlusion remains off.

## Indicative cost

A fresh single-process 1280x720 pair used 40 warmup and 200 measured frames without
validation. This remains smoke evidence rather than a repeated admission set.

| Metric | Pyramid only | Both query oracles | Delta |
|---|---:|---:|---:|
| Wall average | 5.415483 ms | 5.920826 ms | +0.505343 ms |
| CPU GBuffer-record median | 0.0563 ms | 0.1233 ms | +0.0670 ms |
| GPU frame median | 0.352416 ms | 0.366976 ms | +0.014560 ms |
| GPU device-owned query median | — | 0.001024 ms | +0.001024 ms |
| Requested live memory | 1343.478775 MiB | 1343.572525 MiB | +0.093750 MiB |

The wall/CPU-frame samples contain large fence-wait tails and are not suitable for
admission. The isolated device-owned dispatch is approximately one microsecond at
this workload. The 96 KiB memory delta is the complete temporary CPU query, original
result, and device-owned result qualification storage across frame contexts.

## Remaining M7.6 work

The proven projection is now consumed by the existing GPU compaction flow behind the
separate `--experimental-depth-occlusion-rejection` option. Its temporal, off-
frustum, rebuild, and current-build image checks are exact, but the separate query
dispatch is not a performance admission. See
`docs/performance/M7.6-experimental-command-rejection-2026-09-11.md`. The production
route must fuse query and compaction, remove the temporary frame build plus
persistent-history copy and qualification readbacks, and add disocclusion, real
resize, small-bounds, movement, and depth-content-invalidation evidence before
repeated native-4K admission.

No accepted ADR changed.
