# M5.10 Baked-Lighting Contracts — 2026-08-13

Status: accepted foundation slice. This is a data/ownership qualification, not a
production GI image-quality or GPU-performance claim.

## Behavior and architecture

- `iridium.component.baked_lighting_set` / `BLS1` persists a cooked lighting asset
  GUID, diffuse/specular intensity, and independent lightmap, irradiance-volume, and
  visibility contribution switches. The Inspector supports typed Asset Browser
  drag/drop and preserves authored intent independently of residency.
- `iridium.baked-lighting` schema 1 has a required deterministic manifest and
  optional typed lightmap, SH-L2 irradiance-volume, and visibility-volume sections.
  All radiance semantics are scene-linear ACEScg/AP1/D60 and all lengths are metres.
- Lightmap association uses stable scene entity UUID plus mesh primitive GUID. Probe
  and visibility volumes use stable owner UUIDs. Paths, ECS indices, draw indices,
  C++ layouts, and Vulkan handles are absent.
- Scene, geometry, material, light, settings, and tool SHA-256 fingerprints provide
  independent invalidation. The scene itself must also be a hashed asset dependency,
  so CookKey changes follow dependency revision changes while path moves preserve
  association.
- Publication validates the complete product before an atomic generation change.
  Failed revisions retain the last-known-good product; no valid product contributes
  neutral lightmaps, probe irradiance, and visibility.
- Accepted ADR-0011 owns the stable boundary. M10 may add solvers, streaming chunks,
  and GPU representations without changing scene ownership.

## Verification

- Debug and Release build successfully and pass 69/69 tests.
- `BakedLightingProductTests` covers deterministic artifact bytes despite reordered
  bindings, typed round-trip semantics, stable moved dependency identity, dependency
  CookKey changes, independent invalidation domains, malformed/truncated/unknown/
  missing sections, scene dependency validation, and last-known-good retention.
- Core scene tests cover source/cooked component round trips, nullable asset intent,
  nonnegative finite domains, pending dependency load, and source-free cooked scenes.
- M4 and M5 frozen scene contracts retain their historical values and add an explicit
  M5.10 supersession for the new component manifest.
- This slice changes no shader, render pass, descriptor layout, or Vulkan resource;
  Vulkan validation and visual comparison are therefore not applicable.

## Five-process Release contract benchmark

The benchmark product contains one 8192 directional lightmap atlas descriptor,
100,000 stable entity/primitive bindings, four irradiance volumes, four visibility
volumes, 48 MiB of opaque typed payload, and 5,600,616 bytes of in-memory descriptor
storage. Its serialized cooked artifact is 55,934,252 bytes. Each process used five
warmups and 25 measured iterations.

| Operation | Median of process medians | Process-median range | Worst process p95 |
|---|---:|---:|---:|
| Typed load and full validation | 8.9649 ms | 8.9039–8.9991 ms | 11.2757 ms |
| Validate and atomic publication | 8.9994 ms | 8.9406–9.0093 ms | 10.6739 ms |

The current foundation copies a complete product during validation/publication. That
is acceptable for an offline/load boundary but is explicitly not a render-thread
streaming design. M10 owns asynchronous chunk I/O, independently resident sections,
upload budgets, and final CPU/GPU memory measurement for real solver outputs.

## Deferrals and risks

- No baker, lightmap UV generator, GI solver, streaming scheduler, or GPU sampling is
  implemented here; those remain M10 work.
- The descriptor/payload formats are deliberately typed but not a promise that every
  future solver shares one encoding. New representations require versioned sections
  or a superseding schema.
- The M5.10 product reader lives in the cooked asset layer; the JSON/editor-free M4
  runtime scene registry remains source-free and does not acquire source parsers.
