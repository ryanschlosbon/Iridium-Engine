# M7.5 Deployable LOD Oracle Separation — 2026-09-02

## Decision

Keep generated main-view LOD experimental and retain LOD0 as the production default,
but accept the deployable-path overhead repair. Exact CPU LOD command reconstruction
is now a qualification mode rather than unconditional work in every experimental LOD
frame. Vulkan validation enables it automatically; a no-validation evidence run can
request it explicitly with `--gpu-lod-qualification-oracle`. The effective mode is
recorded as `_oracle_0` or `_oracle_1` in capture/profile quality provenance.

The GPU selector also computes the invariant bounds projection for a primitive once
per LOD chain instead of once per child level. This preserves the existing bounded
error, topology, hysteresis, history, and fail-visible contracts.

The repair moves the frozen native-4K near/mid/far candidate from a measured 1.5206%
wall-time regression to effective parity: maximum LOD 0 measures 3.127328 ms and the
2-pixel route 3.128511 ms, a +0.001183 ms / +0.0378% difference. That is not a
material performance win. Complete GPU median remains 0.56% higher and the candidate
tails are worse, so production admission remains held. Physical coarser-resident
fallback is also still required for M7.5 completion.

No ADR is changed. ADR-0014's generation-safe identity, publication, and per-content
maximum-LOD contracts remain authoritative.

## Architecture and controls

- `ApplicationConfig` owns the explicit `gpuLodQualificationOracle` request and
  parses `--gpu-lod-qualification-oracle`.
- The application enables the backend oracle when Vulkan validation is active or the
  explicit request is present. Normal Release/no-validation LOD runs leave it off.
- `RenderBackendConfig` carries one backend-neutral
  `enableGpuLodQualificationOracle` policy bit. Vulkan-specific behavior remains in
  `VulkanVertexBackend`.
- Visibility bin parity remains available in both modes. Only the expensive CPU LOD
  selection, expected-command table, command-buffer copy, LOD mismatch comparison,
  and LOD oracle/history counters are conditional.
- Qualification mode still throws on any device/CPU LOD command disagreement.
- `gpu_scene_frustum_compact.comp` precomputes base-bounds clip extrema and matrix
  norms once, then evaluates each child error against that shared projection.

The default non-experimental engine path remains unchanged: zero experimental error
still renders LOD0 and does not allocate or update LOD history.

## Native-4K deployable-path performance

The final set uses the frozen `m7_three_dense_near_mid_far_v1` fixture, native
3840x2160 Release rendering, no reconstruction, validation disabled, oracle disabled,
CPU/GPU profiling enabled, 500 warmup plus 10,000 measured frames, five fresh
processes per route, and alternating route order. Both routes retain the experimental
history allocation so the comparison isolates maximum LOD 0 versus the 2-pixel/full-
chain selector. Pre/post NVIDIA telemetry reports P0, 2580 MHz SM, 10501 MHz memory,
3–4% idle utilization, and no observed external contention.

## Disposition

- Accept the qualification/deployable split and invariant projection reuse.
- Keep the exact oracle on automatically for validation and explicitly available for
  no-validation parity evidence; do not charge it to production timing.
- Keep generated LOD and 2-pixel selection experimental. Effective wall parity is
  insufficient for promotion when complete GPU time and tails still regress.
- Do not loosen the image-error threshold to manufacture a performance win.
- Next M7.5 work remains physical coarser-resident fallback and a workload where
  triangle reduction is large enough to exceed selection/compaction cost reliably.
- Fine-grained child CookKeys remain M7.9; independent shadow/probe LOD and shadow
  fidelity remain M7.7.

M7.5 remains active. No roadmap slice is accepted and no ADR is superseded.
