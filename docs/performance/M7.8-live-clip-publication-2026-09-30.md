# M7.8 live CPU directional clip publication

Date: 2026-09-30
Status: CPU publication checkpoint; per-slot GPU upload/graph scheduling still open

## Changed behavior and architecture

Under `--experimental-virtual-shadow-resources`, the Vulkan backend now produces
a CPU clip packet from the actual selected directional light, active view camera
and resolved world-space caster bounds before the conventional shadow cache-hit
early return. Only the first selected directional light is qualified here; this
does not imply shared multi-light storage or virtual sampling. Normal/default-off
frames do none of this work and conventional shadow output remains unchanged.

The backend-neutral `DirectionalVirtualShadowClipPublisher` owns monotonic
projection revisions. It builds a conservative light-space depth envelope from
all submitted caster spheres plus a receiver interval centered on the camera with
half-span equal to the coarsest XY world span. Padding defaults to 16 world units;
depth limits round outward in 256-unit buckets. Existing depth limits are retained
while they contain the required envelope. Growth advances the revision; shrinkage
does not churn the projection. Light owner/direction, level/span/resolution/page
policy or required layers also advance the revision. Reset does not recycle a
revision. Commit is transactional after complete clip validation.

Unknown, negative-radius or nonfinite caster bounds suppress the whole packet
instead of assuming a safe depth fit. Invalid policy throws before committing.
Caster content changes propagate their revision without changing the projection
when bounds still fit. The current backend has no static/dynamic partition for
this packet: both layers receive the complete caster-content key conservatively.
This is correctness-first CPU publication, not per-page invalidation efficiency.
The depth envelope can over-cover and grow; practical scene policies, precision
and multi-light/multi-view ownership require later qualification.

The backend retains a reusable caster-bound scratch vector and one CPU packet;
no additional GPU buffer or image is allocated. Four clip levels use 128x128 pages
each; virtual resolution is the configured page size times 128, so the stack fits
the existing 65,536-cell workspace. CPU scope
`cpu.render.virtual-shadow.clip-publication` includes bound collection, caster-key
construction and publication. Counters expose `shadow.virtual.clip.available`,
`levels`, `projection_revision` and `caster_bounds`.

Files/interfaces: `renderer/rhi/VirtualShadowMap.h/.cpp` (publisher/bounds),
`renderer/vulkan/VulkanVertexBackend.h/.cpp` (live hook, retained state, counters),
`tests/renderer/VirtualShadowMapTests.cpp` (state transitions), and the M5 latest
contract fingerprint gate. No shader ABI or RHI renderer virtual method changes.

## Verification

Full Debug and Release builds succeed; the CPU virtual-shadow suite passes 17/17
cases, including depth growth/retention, caster revision propagation, unknown-bound
suppression and recovery, rotation, owner replacement, reset and failed-policy
transactionality. All 78 repository tests pass in each configuration.

The clip builder remains approximately 1.48 us Debug / 0.19 us Release per four-
level plan in the existing standalone benchmark. That is not the cost of the
complete publisher, which also visits casters and conservatively builds a content
key. GPU storage remains 88.753 MiB under the resource switch and zero when off.
No matched visual or whole-frame performance improvement is claimed.

A twelve-frame Debug launch at 1280x720 with validation exits zero and has an
empty error log. All twelve actual scene frames report one caster bound, a valid
four-level packet and stable projection revision 1, including cache-hit frames.
The complete publication scope measures 11.6 us median / 37.5 us maximum in this
tiny fixture; that is not a representative large-scene or matched overhead gate.
The short run averages 9.669066 ms CPU per frame, including startup-frame noise.
Local evidence: `out/m7_8_live_clip_profile_20260930.jsonl` and corresponding
`m7_8_live_clip_startup_20260930.log/.err`.

## Next integration gate

Per-slot packed uploads and render-graph scheduling are deliberately not part of
this checkpoint. The current executor does not bind external buffers as owned
physical resources; resource binding and transfer/compute hazard tracking must be
made explicit before recording live uploads or dispatching full-view accumulation.
The retained packet must be captured for its frame slot rather than read later
from mutable global CPU state. Qualify actual packet/readback parity, camera/light
changes, unknown bounds, resize and overlapping slots at native 4K. Page residency,
raster and virtual lighting sampling remain later M7.8 gates. Forward/transparency
receivers still need explicit coverage or conventional fallback.

M7.8 remains active, conventional shadows remain in use, and no accepted ADR is
superseded. Roadmap/context/plan/ADR/frame-budget records point to this checkpoint.
