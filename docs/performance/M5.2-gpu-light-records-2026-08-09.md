# M5.2 GPU light records - 2026-08-09

Status: Accepted M5.2 extraction, upload, and RHI diagnostic slice.

Machine-readable Release extraction results are in
`docs/performance/data/M5.2-light-extraction-2026-08-08.json`. Vulkan validation,
profiles, captures, and the strict M5.0 comparison remain under
`out/benchmarks/m5.2/`.

## Accepted architecture and behavior

- `PackedGpuLight` is a backend-neutral, 16-byte-aligned, 64-byte std430 record:
  position/range, scale-independent surface-to-light direction/outer-cone cosine,
  AP1-normalized color/physical intensity, and shape/metadata.
- Stable scene UUIDs own deterministic slots. Initial publication is UUID ordered;
  incremental edits retain slots; removal writes a revised zero tombstone; a full
  world swap resets ownership deterministically.
- Local authored `-Z` emission maps to record `+Z` surface-to-light direction.
  Hierarchy rotation ignores nonuniform and negative scale; position uses the
  derived world transform.
- Invalid, nonfinite, missing-transform, zero-luminance, unsupported Area, and
  capacity-exhausted lights are omitted with structured diagnostics. No stale
  record remains visible.
- Capacity starts at 256, grows geometrically at a fence-safe frame boundary, and
  is capped by both 65,536 records and `maxStorageBufferRange`.
- Vulkan owns one persistently mapped coherent storage buffer per frame context.
  Per-frame revision tables coalesce and write only changed contiguous ranges.
  Every descriptor always has a valid zero-initialized buffer, including scenes
  with no lights.
- RHI capabilities, frame packets, exact counters, CPU ranges, runtime metadata,
  and `buffer.light_gpu` memory attribution expose the path without putting Vulkan
  state in scene/runtime contracts.

M5.2 does not consume the records in lighting math. The fixed M5.0 direct-light
oracle remains until M5.4, so this slice deliberately changes no pixels.

## Integrated Vulkan and image verification

- Debug and Release configure/build pass; all 64 CTests pass in both configurations.
- A Debug validation run with 4,096 authored validation lights reports capacity
  4,096 and active count 4,096. Frame 1 extracts and uploads one 262,144-byte range;
  frame 2 uploads the same range into the other fence-owned frame buffer; frames 3
  and 4 upload zero bytes/ranges. No counter or GPU-range overflow occurs.
- That run reports 524,288 requested/committed live light-buffer bytes. The
  557,056-byte peak is the deliberate fence-safe overlap of the initial 256-record
  tables and their replacements during growth.
- A separate zero-light Debug validation/capture run binds the 32 KiB fallback and
  completes without a Vulkan validation message.
- A Release, validation-enabled, 3840x2160 sample-car run uses the accepted M5.0
  50-warmup/300-measured protocol and captures measured frame 299. Its final-SDR
  SHA-256 remains
  `fb0a37e71ab557a12e7a42609e6544b9f8d9c0de1b9d304ff3f689ea9b1f14d4`.
  Strict comparison reports maximum RGBA delta 0, changed pixels 0, and mean luma
  SSIM 1.0.

The pre-existing retained sample-car allocation discrepancy remains: the 300-frame
validation profile reports one 8-byte allocation on every retained frame, with a
maximum of two calls/120 bytes. M5.2 extraction itself is allocation-free in every
steady benchmark; this does not close the broader M5.0 discrepancy.

## Roadmap and architecture status

M5.2 implements ADR-0007's backend-neutral UUID-owned light records and retains the
one future shared assignment direction. It accepts no new ADR and supersedes no
accepted ADR. The historical M5.0 shader hashes remain frozen; a named
`m5_2Supersession` block records the current ABI-declaration shader/SPIR-V hashes.
M5 remains In Progress; M5.3 shared clustered assignment is next.
