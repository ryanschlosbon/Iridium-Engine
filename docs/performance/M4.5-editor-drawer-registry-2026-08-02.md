# M4.5 Editor Drawer Registry Evidence — 2026-08-02

## Scope

Release measurements cover construction of the frozen core editor component and
drawer registries plus descriptor-driven Inspector access at 10k and 100k entities.
The benchmark target no longer links ImGui and no longer hashes RTTI pool names.

Raw evidence:
`docs/performance/data/M4.5-editor-drawer-registry-2026-08-02.json`.

## Results

| Case | Scale | Median | p95 | p99 | Median allocations | Requested bytes |
|---|---:|---:|---:|---:|---:|---:|
| Registry construction | one construction | 0.0057 ms | 0.0088 ms | 0.0116 ms | 46 | 13,448 |
| Descriptor/custom-drawer dispatch | 10k entities | 44.735 ns/op | 66.653 ns/op | 70.658 ns/op | 0 | 0 |
| Descriptor/custom-drawer dispatch | 100k entities | 168.911 ns/op | 178.060 ns/op | 182.173 ns/op | 0 | 0 |

The one-time registry construction median is 10.6% of the frozen M3 0.0537 ms
editor-build median. The hot Inspector traversal performs no C++ heap allocations.

The old `editor_inspector_descriptor_construction` workload only iterated RTTI pool
entries and called `getVoid`. The M4.5 workload performs stable descriptor
enumeration, typed component presence/access, and custom-drawer lookup. Its 10k and
100k values are therefore retained under the historical case name for continuity
but are not presented as a like-for-like speedup over M4.0/M4.3.

## Architecture outcome

- Runtime ECS component types and pools contain no editor or ImGui hooks.
- Transform, Relationship, Mesh, and Light custom UI is registered by stable ID.
- Components without a custom drawer use ordered property metadata.
- The Inspector loop contains no RTTI-name or component-ID presentation switch.
- A small contiguous drawer table is retained because the core set has four entries;
  its measured linear lookup is faster and simpler than binary lookup at this scale.

## Integration and interactive verification

An additional visible Release run exercised the selected material-lab entity at
3840x2160 for 100 warm-up and 300 measured frames with
`VK_LAYER_KHRONOS_validation`. It completed with zero dropped frames and no Vulkan
validation message. Editor build was 0.0626 / 0.1271 / 0.3359 ms
median/p95/p99; GPU UI was 0.1157 / 0.1270 / 1.7531 ms; total GPU frame was
1.7736 / 3.5835 / 4.0991 ms. Steady C++ allocation median was zero. Raw profile:
`out/m4.5-release-editor-4k-validation.jsonl`.

That deterministic benchmark mode intentionally replaces editor panels with its
benchmark-output window. It validates the 4K Vulkan/UI transport but is not claimed
as Inspector interaction evidence.

The normal editor path was then exercised at both maximized 4K-monitor layout and
1280x720 compact layout with a selected Mesh entity. The following passed without a
crash, stale selection, clipped required controls, or validation message:

- Mesh thumbnail and all 22 material slots through paging and scrolling;
- grid/list switching and zoom from level 2 to level 3;
- model picker open/cancel and material override picker open/cancel;
- descriptor-driven Add Component showing only Light for the selected entity;
- Light creation, custom Light drawer presentation, and Light removal;
- restoration of the original component set after the temporary Light test.

Representative captures are under `out/` with the
`m4.5-editor-*.png` prefix. A final normal-editor Release profile collected 300
measured 1280x720 frames with validation enabled and zero dropped frames. Editor
build was 0.1021 / 0.1367 / 0.1523 ms median/p95/p99; GPU UI was
0.0174 / 0.0184 / 0.0205 ms; total GPU frame was 0.0528 / 0.0623 / 0.0823 ms.
Whole-editor C++ allocations were 126 median / 144 p95 calls per frame; this scope
includes every normal editor panel and asset-browser UI, while the isolated M4.5
descriptor/drawer dispatch benchmark remains allocation-free. Raw profile:
`out/m4.5-release-editor-normal-compact-validation.jsonl`.
