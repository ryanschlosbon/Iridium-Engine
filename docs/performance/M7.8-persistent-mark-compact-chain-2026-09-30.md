# M7.8 persistent receiver-marking and compaction chain

Date: 2026-09-30
Status: accepted Vulkan ownership and direct compute-chain checkpoint; M7.8 active

## Behavior and ownership

`VulkanVirtualShadowMarkingPass` owns the raw directional marker and hierarchical
compactor pipelines, their layouts, one bounded descriptor pool, and immutable
descriptor sets for each frame slot. `VulkanVirtualShadowResources` initializes
this owner against its existing device-local working sets behind
`--experimental-virtual-shadow-resources`. Cleanup destroys the compute owner
before its buffers. The shared implementation is compiled into the engine and
the hardware qualification executable.

The record operation takes a frame slot, receiver/clip counts, coarsest clip level,
and guard-band width. It emits the marker, a compute dependency, then clear,
projection, hierarchical address ordering, duplicate reduction, rank ordering,
dropped-coverage reduction, and bounded output. No raw-mark download, host sort,
intermediate submission, descriptor update, or allocation is required while
recording. Scratch work scales to the next power of two of the current receiver
count, with a minimum of 256. Empty input clears telemetry and publishes zero
requests; consumers must obey the published count because unused output bytes
retain their prior contents.

The caller owns frame-fence reuse and input publication. Transfer/compute input
writes are synchronized before marking; each compute stage publishes writes to
the next stage. A later transfer, raster, or other consumer must supply its own
appropriate dependency. The descriptor sets select independent storage for each
frame and are never rewritten while in flight.

| 4,096 multi-level/duplicate receivers | 32 | 0.087488 ms | 0.087456 ms |
| 65,536 unique page-center receivers | 4,096 | 0.148512 ms | 0.147264 ms |

Five timestamped full-input runs follow warm-up/reuse checks. Timestamps cover
the shared marker plus complete compaction chain, including its input dependency,
and exclude transfer upload/readback and pipeline/buffer allocation. These are
standalone compute timings, not whole-frame admission measurements. The prior
compaction-only baseline is approximately 0.146 ms at full capacity.

Each fixture reuses two persistent monolithic buffers and their immutable sets
across full, one-receiver, empty, 513-receiver, empty, and repeated full frames.
The CPU oracle exactly matches page coordinates, clip/mip, coverage, priority,
required layers, unique/output counts, bounded overflow, and dropped coverage.
Empty frames publish zero counts after populated frames. Existing malformed-mark,
saturation, ordering, clip-scroll, and compactor tests continue to pass. The
validation callback records zero errors with synchronization validation enabled.
Both engine configurations build successfully, and all 78 repository tests pass
in Debug and Release, including the refreshed M5 current-contract hashes.
These runs serialize submissions for deterministic readback; simultaneous frame
overlap remains part of live-producer qualification.

An eight-frame 1280x720 Debug engine launch with validation and the resource switch
exits with code zero. Its error log is empty. The profiler still reports exactly
75,759,616 bytes for the pool, 262,144 for the table, and 17,042,496 for two working
sets: 93,064,256 bytes (88.753 MiB) total. Descriptor/pipeline driver allocations
are outside these engine-buffer/image counters. The short launch averages
5.307662 ms and is lifecycle evidence only, with no matched performance claim.
Local artifacts are `out/m7_8_chain_profile_20260930.jsonl`,
