# M7.6 depth-history ownership — 2026-09-09

## Safety prerequisite

The original eligibility helper accepted caller-provided age and booleans, but
could not distinguish scene and asset-viewer images of equal extent. It also could
not invalidate depth when an occluder other than the tested object moved or vanished.
Before live history allocation, the CPU-side depth-pyramid contract advances to
version 2 with explicit producer ownership and render-submission serials.

`DepthPyramidHistoryOwner` carries view identity, scene epoch, aggregate depth-content
revision, projection revision and camera-reset revision. Missing view/scene/depth
identity fails visible. Current and produced history must match each identity;
forward/reverse depth conventions must be valid and equal. Submission serials must
be nonzero and exactly adjacent, using ordered subtraction so wraparound, future
history, same-frame feedback and throttled/skipped views cannot be accepted.

New stable reasons identify invalid ownership, different view/scene, changed depth
content/projection and depth-convention mismatch. Reset-revision differences use
the existing camera-cut reason. Existing extent, motion, near-plane, residency and
transform checks remain. Existing rejection values are preserved; new ones append.

## Integration obligations

These are CPU metadata, not GPU material/scene ABI or serialized asset changes.
No production consumer exists yet. The producer must stamp metadata only for the
depth actually rendered, and revision tracking must include every depth-affecting
geometry, transform, coverage, residency and visibility change. A change journal
for the candidate alone is insufficient. Do not substitute a wrapping frame-slot
index or local per-view counter for a global render-submission serial.

This deliberately invalidates all history when depth content changes. More selective
moving-occluder handling needs separate proof. Camera motion/disocclusion safety,
GPU completion/resource hazards, image generations, graph ownership and per-view
resource storage are not established by matching metadata alone. Existing motion
checks still require conservative caller inputs; no claim of complete temporal
occlusion correctness is made here.
